# 폴링 자동화 (Edge Function + pg_cron) — 설계

> [매치 폴링](2026-08-09-매치-폴링-design.md)으로 만든 로컬 스크립트를 Supabase 서버에서 자동으로 돌게 옮긴다.

## 왜 필요한가

PUBG API는 최근 14일치만 제공한다. 지금은 사람이 `node scripts/poll-matches.mjs`를 직접 쳐야 하고, 잊거나 PC가 꺼져 있으면 그 사이 내전이 영영 사라진다.

이건 가정이 아니다. 폴링을 처음 돌린 날, **07-26 내전 4경기 중 2경기가 이미 사라진 뒤였다.** 하루만 늦었어도 그날 전체가 날아갔다. 내전이 주 2일이므로 2주만 손을 놓으면 4번의 내전이 유실된다.

## 실행 시각

**매주 목요일·일요일 한국시간 23:30** (UTC 14:30). 내전은 한국시간 20:00~21:40에 열리므로(실측: 08-02 기준 20:01~21:39), 끝나고 약 2시간 뒤에 수집한다.

pg_cron 표현식: `30 14 * * 0,4` — Supabase 의 기본 타임존이 UTC 이므로 KST 에서 9시간을 뺀다. 23:30 - 9 = 14:30 으로 날짜가 넘어가지 않아 요일도 그대로다.

## 실행 시간이 이 설계의 제약이다

Edge Function 은 실행 시간과 CPU 에 제한이 있다. 그래서 "한 번 실행에 매치를 몇 건 여는가"가 설계를 좌우한다.

### 측정한 것

내전 참가 상위 20명이 **14일간 뛴 경기가 2721건**이다. 내전은 그중 10경기뿐이고 나머지는 전부 개인 랭크다. 하루 194건이므로 목→일 3.5일 간격이면 **한 번에 약 680건**을 열어야 한다. 응답마다 참가자 64명이 들어 있어 조회 시간뿐 아니라 JSON 파싱 부담도 크다. 이대로는 제한을 넘긴다.

### 데이터가 해법을 보여줬다

| 씨앗 후보 | 14일 총 경기 | 내전 참가 |
|---|---|---|
| `Ez_LaPaz` | 279 | 10/10 |
| `Ez_DanE` | 226 | 10/10 |
| … | | |
| `Ez_MACHO-` | 60 | 10/10 |
| `Ez_2pan4pan_` | 52 | 10/10 |
| `Ez_Grim` | 39 | 10/10 |

**상위 20명 전원이 내전 10경기에 빠짐없이 나왔다.** 씨앗으로서의 가치는 같은데 비용은 7배까지 차이난다. `Ez_LaPaz`를 쓰면 랭크 279경기를 열어야 하지만 `Ez_Grim`은 39경기뿐이고, 내전엔 똑같이 나온다.

그래서 씨앗 기준을 **"내전에 자주 나오는 사람"에서 "내전에 자주 나오면서 랭크는 적게 하는 사람"으로** 바꾼다.

### 매치 목록은 최신순이다 (실측)

`Ez_Grim`의 39경기가 `[0] 08-09T12:38` → `[38] 07-26T14:39`로 정확히 내림차순이었다. 따라서 목록을 위에서부터 훑다가 기준 시각보다 오래된 매치를 만나면 **그 사람은 거기서 멈춰도 된다.**

### 두 가지를 합친 결과

| 방식 | 한 번에 여는 매치 | 예상 시간 |
|---|---|---|
| 참가 상위 20명 × 마지막 폴링 이후(3.5일) | 680건 | 3분+ (제한 초과) |
| 가벼운 8명 × 마지막 폴링 이후(3.5일) | 148건 | 40초 |
| **가벼운 8명 × 24시간** | **약 40건** | **15초 내외** |

**"24시간만 본다"의 대가**: 폴링이 한 번 실패하면 그날 내전을 복구할 수 없다. 다음 실행은 그날 것만 보기 때문이다.

이걸 받아들이되 만회 경로를 남긴다 — 되돌아볼 기간을 인자로 조절할 수 있게 만들고(`--since-hours`), 실패하면 디스코드로 알린다. 알림을 받으면 로컬에서 `--since-hours=336`(14일)으로 수동 실행해 만회한다. **조용한 영구 유실을, 알림 받고 손으로 고치는 일로 바꾸는 것이다.**

## 파이프라인

```
pg_cron  (목·일 UTC 14:30)
   │  net.http_post 로 함수 호출
   ▼
Edge Function  poll-matches
   │
   ├─ 1. 씨앗 선정 (2단계)
   │      a. 내전 참가 상위 30명을 DB 에서 고른다
   │      b. Players 로 조회한다 (10명씩 3회)
   │      c. 응답에 들어 있는 매치 목록 길이로 가벼운 8명을 고른다
   │
   ├─ 2. 각 씨앗의 매치 목록을 위에서부터 훑는다
   │      기준 시각(기본 24시간 전)보다 오래된 매치를 만나면 그 사람은 멈춘다
   │
   ├─ 3. polled_matches 에 없는 matchId 만 조회 → 내전 판별 → 저장
   │
   └─ 4. polling_runs 에 기록하고 결과를 디스코드로 알린다
```

**씨앗을 두 단계로 고르는 것이 핵심이다.** DB 의 참가 기록만으로는 그 사람이 랭크를 얼마나 하는지 알 수 없다. 그런데 Players 응답에 매치 목록이 통째로 들어 있어 **조회하고 나면 공짜로 알게 된다.** 후보 30명을 조회한 뒤 가벼운 8명만 실제로 매치를 여니 추가 API 호출이 없다.

Players 엔드포인트는 분당 10회 제한이라 30명 조회에 3회(약 13초)가 든다. Matches 엔드포인트는 제한이 없다.

## 스키마

`supabase/migrations/0006_polling_automation.sql`. 0001~0005 는 건드리지 않는다.

```sql
create extension if not exists pg_cron;
create extension if not exists pg_net;

create table if not exists polling_runs (
  id uuid primary key default gen_random_uuid(),
  started_at timestamptz not null default now(),
  finished_at timestamptz,
  trigger text not null,              -- 'cron' | 'manual'
  since_hours integer not null,       -- 얼마나 되돌아봤는지
  seeds_used integer,
  matches_examined integer,
  scrims_found integer,
  succeeded boolean,
  error_message text
);

create index if not exists polling_runs_started_idx on polling_runs (started_at desc);

alter table polling_runs enable row level security;
-- 내부 운영 기록이라 공개 읽기 정책을 만들지 않는다.
revoke select on polling_runs from anon;
revoke select on polling_runs from authenticated;
```

`polling_runs`에 남는 "마지막 성공 시각"은 만회 실행에서 기간을 얼마나 넓혀야 하는지 판단하는 근거가 된다.

## 코드 구조

로직을 한 벌만 둔다. 판별·해석 로직(`matches.mjs`)은 **외부 의존이 전혀 없는 순수 함수**라 Deno 와 Node 양쪽에서 그대로 돈다.

| 파일 | 역할 |
|---|---|
| `supabase/functions/_shared/matches.mjs` | 순수 로직 (기존 `scripts/lib/matches.mjs` 를 이곳으로 옮긴다) |
| `supabase/functions/_shared/polling.mjs` | 씨앗 선정, 매치 목록 훑기 등 양쪽이 공유하는 로직 |
| `supabase/functions/poll-matches/index.ts` | Edge Function 진입점 (HTTP 요청 처리, Deno 전용) |
| `scripts/lib/matches.mjs` | `_shared/matches.mjs` 를 다시 내보내기만 한다 |
| `scripts/poll-matches.mjs` | 로컬 실행용. 공유 로직을 쓰고 인자를 받는다 |

`supabase/functions/_shared/` 는 Supabase 가 정한 관례이고, 배포할 때 함수와 함께 올라간다. Node 스크립트는 상대 경로로 같은 파일을 가져오므로 **로직이 갈라질 수 없다.**

공유 파일은 `.ts` 가 아니라 `.mjs` 로 둔다. Deno 는 `.mjs` 를 읽지만 Node 는 `.ts` 를 그대로 못 읽기 때문이다. 대신 타입은 없다 — 이 파일들은 이미 vitest 로 덮여 있어 큰 손해가 아니다.

`scripts/lib/roster.mjs` 의 `chunk` 도 함수가 쓰므로 `_shared/polling.mjs` 로 옮긴다. `roster.mjs` 의 나머지(TSV 파싱, 이름 변형)는 클랜원 등록 전용이라 그대로 둔다.

로컬 스크립트를 남기는 이유는 세 가지다 — 자동 실행이 실패했을 때 기간을 넓혀 만회하고, 실데이터로 디버깅하고, 배포 결과가 로컬과 같은지 대조하기 위해서다.

## 배포와 권한

**인증**: Supabase 대시보드(Account → Access Tokens)에서 발급한 토큰을 `.env.local` 에 `SUPABASE_ACCESS_TOKEN` 으로 넣는다. 그러면 브라우저 로그인 없이 배포할 수 있다.

**CLI 설치는 불필요하다** — `npx supabase` 로 바로 쓸 수 있다(2.113.0 확인).

**함수가 쓸 비밀값**은 Supabase 에 따로 등록한다. Edge Function 은 `.env.local` 을 못 읽는다.

- `PUBG_API_KEY`
- `DISCORD_WEBHOOK_URL`
- `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` 는 Supabase 가 자동으로 주입한다

**함수 호출 권한**: pg_cron 이 `net.http_post` 로 부를 때 `Authorization: Bearer <service_role_key>` 헤더를 붙인다. 이 키를 SQL 안에 그대로 적으면 마이그레이션 파일에 비밀값이 들어가므로, **Supabase Vault 에 넣고 SQL 에서는 이름으로 참조한다.**

## 실패 처리

- **매치 하나 조회 실패** — 그 매치만 건너뛰고 계속한다. 4경기 중 1경기가 실패해도 3경기는 저장된다.
- **속도 제한(429)** — Players 조회에서만 발생한다. 60초 쉬고 재시도하되, 실행 시간 제한이 있으므로 **한 번만** 재시도하고 그래도 안 되면 실패로 기록한다. (로컬 스크립트는 계속 재시도해도 된다.)
- **함수 전체 실패** — `polling_runs` 에 `succeeded = false` 와 에러를 남기고 디스코드로 알린다.
- **작업량 초과 대비** — 한 번에 여는 매치에 상한(기본 200건)을 둔다. 넘으면 거기서 멈추고 남은 건수를 기록·알림한다. `polled_matches` 가 이미 진행 상황을 갖고 있어 다음 실행이 이어받는다.
- **멱등성** — `pubg_match_id` 가 기본키라 여러 번 실행해도 중복되지 않는다.

## 알림

디스코드 웹훅 URL 하나만 있으면 된다. 채널 설정에서 발급하며 **봇을 만들 필요가 없다** — 클랜원 명단을 뽑을 때 부담스러워 배제했던 그 설정과는 다르다.

| 상황 | 알림 |
|---|---|
| 내전 발견 | `08-09 내전 4경기 수집 (참가 64명, 미등록 1명: Ez_HxxJxx)` |
| 실패 | `폴링 실패 — <에러>. node scripts/poll-matches.mjs --since-hours=336 으로 만회할 것` |
| 상한 초과 | `매치 200건까지만 처리함. 남은 건은 다음 실행에서 이어받음` |
| 내전 없음 | 보내지 않는다 — 내전 없는 날이 정상이라 매번 알리면 소음이 된다 |

미등록 참가자를 알림에 넣는 이유는, 그게 명단을 고치는 신호이기 때문이다. 지금까지 이 목록이 명단 오류 여러 건을 잡아냈다.

## 검증

**순수 로직**은 기존 vitest 테스트가 그대로 덮는다. 파일을 옮기므로 import 경로만 바뀐다.

**함수 배포 후**에는 수동으로 호출해 **로컬 실행과 같은 결과가 나오는지** 대조한다. 이미 10경기가 저장돼 있으므로, 같은 기간을 다시 돌려도 새로 저장되는 게 없어야 한다(멱등성). `polling_runs` 에 행이 생기고 `succeeded = true` 인지도 함께 본다.

**pg_cron 이 실제로 부르는지**는 예약 시각을 잠깐 몇 분 뒤로 당겨 한 번 돌려보고 `polling_runs` 에 `trigger = 'cron'` 행이 생기는지로 확인한다. 확인한 뒤 원래 시각으로 되돌린다. **예약해놓고 목요일까지 기다렸다가 안 돌았다는 걸 발견하는 것이 최악이다.**

## 이번 범위가 아닌 것

- **과거 내전 스크린샷 입력** — 별도 세션
- **내전 세션 묶기(3단계)와 대시보드 연동(4단계)**
- **알림 채널 확장** — 디스코드 하나로 시작한다
- **실행 이력 화면** — `polling_runs` 를 눈으로 보는 UI 는 만들지 않는다. 필요하면 대시보드 작업 때 붙인다.
