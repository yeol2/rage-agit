# 02 팀 구성 테이블 — 티어별/전체 리롤

## 배경

02 팀 구성 테이블은 배정(팀 번호 매기기), 드래그 스왑, VIP 정렬, 고정(fix)
토글까지 구현됐다(2026-08-19 세 스펙). 고정은 UI에 표시·저장은 되지만 아직
아무것도 그 값을 실제로 "보호"하지 않는다 — 이번 스펙이 그 보호가 의미를
갖는 첫 기능이다: 고정 안 된 사람만 무작위로 뒤섞는 리롤 버튼.

## 범위

**포함**:
- 1~4티어 각각에 대한 "N티어 리롤" 버튼 4개. 그 티어 칼럼 안에서
  `fixed=false`인 엔트리끼리만 팀 번호를 무작위로 재배치한다. `fixed=true`인
  사람은 자리도, 팀 번호도 그대로 유지된다.
- "전체 리롤" 버튼 1개. 1~4티어 각각에 대해 위 셔플을 독립적으로 실행한다
  (티어 간 사람 이동은 없다 — 4개 버튼을 한 번에 누른 것과 동일).
- 오른쪽 버튼 세로 칼럼에 "VIP 정렬" 아래로 다섯 버튼 추가: 전체 리롤, 1티어
  리롤, 2티어 리롤, 3티어 리롤, 4티어 리롤.

**제외**:
- 확인 다이얼로그, 실행 취소(undo) — VIP 정렬과 동일하게 클릭 즉시 적용.
  리롤은 매번 랜덤이라 멱등은 아니지만, 다시 눌러 재시도하는 것으로 충분하다.
- 고정된 사람이 하나도 없는 티어 전체 리롤이나, 고정 안 된 사람이 0~1명이라
  섞을 게 없는 경우에 대한 별도 안내 — 아무것도 안 바뀌면 그냥 조용히
  아무것도 안 바뀐다(에러 아님).

## 클라이언트 상호작용

버튼을 누르면:
- 로딩 중 해당 버튼(들)은 비활성화.
- 성공 시 서버가 돌려준 최신 entries로 화면 갱신(VIP 정렬과 동일한 패턴 —
  낙관적 업데이트 없이 응답을 그대로 반영).
- 실패 시 에러 메시지 표시, 화면은 그대로(변경 없음이므로 되돌릴 것도 없음).

## API

### `POST /api/scrim-roster/reroll`

`{ rosterId: string, tier?: 1 | 2 | 3 | 4 }`

`tier`를 생략하면 전체 리롤(1~4 각각 독립 셔플), 지정하면 그 티어만.

서버가 `rosterId`로 최신 entries를 다시 조회해 `fixed`/`tier_slot`/
`team_number`를 직접 읽는다 — 클라이언트는 어떤 엔트리를 섞을지 지정하지
않는다(VIP 정렬과 동일, swap API처럼 클라이언트가 특정 id 쌍을 보내는
방식이 아니다). 대상 티어(들) 안에서 `fixed=false`인 엔트리들의
`team_number` 값 집합을 Fisher-Yates로 섞어 재배정한다. `fixed=true`
엔트리와 `team_number`가 없는(미배정) 엔트리는 대상에서 제외.

응답은 vip-sort와 동일한 형태로 전체 entries를 돌려준다.

## 순수 함수 (`lib/scrimRoster.ts`)

```ts
export interface RerollInput {
  id: string;
  tierSlot: 1 | 2 | 3 | 4 | null;
  teamNumber: number | null;
  fixed: boolean;
}

// tiers 생략 시 [1,2,3,4] 전체. 각 티어 안에서 fixed=false 이고 teamNumber가
// 있는 엔트리들의 team_number 값 집합을 무작위로 재분배한다(Fisher-Yates).
// fixed 엔트리는 손대지 않는다(값 집합에도 안 들어감).
export function computeReroll(
  entries: RerollInput[],
  tiers?: Array<1 | 2 | 3 | 4>,
): Map<string, number>
```

무작위성 때문에 유닛 테스트는 셔플 결과의 정확한 값이 아니라 불변식을
검증한다: fixed 엔트리는 `changes`에 절대 안 나타남, 반환된 `team_number`
값의 집합이 섞기 전 그 티어의 unfixed 엔트리들이 가진 값의 집합과 정확히
같음(멤버가 사라지거나 중복되지 않음), tier 지정 시 다른 티어는 전혀 안
건드림.

## 클라이언트 (`components/team-builder/RosterBoard.tsx`)

- 다섯 버튼(전체 리롤, 1~4티어 리롤) 추가 — "VIP 정렬" 버튼과 같은
  스타일/로딩·에러 처리 패턴을 그대로 따른다.
- 각 버튼은 `/api/scrim-roster/reroll`을 해당 `tier`(전체 리롤은 생략)와
  함께 호출하고, 응답 entries로 상태를 교체한다.

## 테스트

- `computeReroll` 유닛 테스트: 위 불변식들(고정 미변경, 값 집합 보존, 티어
  격리) + 참가자 0~1명(섞을 게 없음)일 때 빈 맵 반환.
- `POST /api/scrim-roster/reroll` 라우트: `tier` 없이 호출 시 여러 티어에
  걸쳐 갱신되는지, `tier` 지정 시 다른 티어 `team_number`가 그대로인지,
  fixed 엔트리의 `team_number`가 응답에서도 안 바뀌는지.
- `RosterBoard` 컴포넌트 테스트: 리롤 버튼 클릭 → API 호출 확인 → 응답으로
  entries 갱신되는지, 로딩 중 버튼 비활성화.
