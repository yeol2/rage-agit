# 클랜원 일괄 등록 (219명) — 설계

> [빅뱅배포.md](../빅뱅배포.md)의 API 연동 4단계 중 1단계([클랜원 등록](../sessions/2026-08-09-클랜원등록/클랜원등록.md))의 마무리 작업.
> Phase 1은 스키마와 클랜원 2명만 넣고 끝났다. 이 문서는 실제 클랜원 전체를 채우는 작업을 다룬다.

## 왜 이 작업이 생겼는가

Phase 2(매치 폴링)를 설계하다가 클랜 규모가 약 450명이라는 게 드러났다. 폴링 자체는 클랜원 명단 없이도 시작할 수 있지만(아래 "폴링과의 관계" 참고), 명단이 있어야 수집한 매치 데이터가 사람에게 연결된다.

문제는 디스코드 닉네임 ↔ PUBG IGN 매핑이 아무 데도 정리돼 있지 않았다는 것이다. 이건 API가 알려줄 수 없는 정보라 결국 사람이 채워야 한다. 디스코드 봇으로 자동 추출하는 방법을 검토했으나 봇 생성·권한 설정 부담 때문에 배제했고, **티어별 역할 멤버 목록 스크린샷을 사람이 찍어 전달하고 그것을 옮겨 적는 방식**으로 진행했다.

결과적으로 티어 역할이 부여된 **219명**을 확보했다. 나머지(약 230명)는 티어 역할이 없는 인원이라 이번 범위에서 제외한다 — 내전 참가자는 티어가 있는 사람들이고, 없는 사람이 내전에 나오더라도 데이터는 유실되지 않는다(아래 참고).

## 확보한 데이터

`data/discord-members.raw.tsv` — git에 커밋하지 않는다(`.gitignore`의 `data/`). 디스코드 사용자명 219개는 개인정보이고, 이 파일은 Supabase에 넣기 위한 중간 산물일 뿐이다.

| 컬럼 | 예시 | 출처 |
|---|---|---|
| `tier` | `2.5` | 어느 티어 역할 목록에서 나왔는지 |
| `display_nick` | `Ez_LaPaz(현석/94)` | 화면의 굵은 글씨 (서버 별명) |
| `discord_username` | `dlrpajsep` | 화면의 회색 글씨 (디스코드 사용자명) |
| `ign_guess` | `Ez_LaPaz` | 별명에서 파싱 규칙으로 추출한 PUBG IGN 후보 |
| `note` | `? 0/O 판독` | 판독이 애매하거나 특기사항 |

티어별 인원: 0티어 9 / 1티어 4 / 1.5티어 8 / 2티어 18 / 2.5티어 44 / 3티어 33 / 3.5티어 57 / 4티어 29 / 4.5티어 15 / 청정수 2 = **219명**. 각 화면에 표시된 인원수와 옮겨 적은 개수가 전부 일치하는 것을 확인했다. IGN·디스코드 사용자명·별명 모두 중복이 없다.

### IGN 추출 규칙

별명에서 IGN을 뽑는 규칙은 실제 데이터를 보며 다듬었다:

- `Ez_`로 시작하지 않는 별명은 제외한다 (`상사님`, `CheoL` 등 — 클랜 태그를 안 단 사람)
- 괄호 안 내용(출생연도, 한글 별명)과 이모지는 제거한다
- 괄호 밖에 붙은 한글도 제거한다 (`Ez_KimSS쓰쓰` → `Ez_KimSS`, `Ez_Gimli 김리` → `Ez_Gimli`)
- 끝에 붙은 `-`나 `_`는 IGN의 일부이므로 유지한다 (`Ez_AT-`, `Ez_02_`)
- 본/부 계정을 함께 적어둔 경우 앞의 것만 채용하고 부계정은 버린다 (`Ez_DanE/Ez_Dan2` → `Ez_DanE`)

**부계정을 버리는 것은 의도된 결정이다.** Phase 1에서 `member_pubg_accounts`를 1:N으로 설계한 이유가 바로 부계정 통합인데, 여기서는 일부러 쓰지 않는다 — 별명에 적힌 부계정 표기는 형식이 제각각이라(`본:/부:`, `/`, `&`, `부계`) 신뢰하기 어렵고, 병합은 나중에 본인 확인을 거쳐 처리하는 편이 정확하다. 그때 `member_pubg_accounts`에 행을 하나 추가하면 되고, 스키마는 이미 그것을 지원한다.

## 파이프라인

```
data/discord-members.raw.tsv  (219명, 사람이 옮겨 적은 원본)
        │
        ├─ scripts/verify-pubg-igns.mjs   (PUBG API 조회)
        ▼
data/verified-igns.tsv   (IGN 확인 + accountId 확보)
data/failed-igns.tsv     (조회 실패 — 사람이 확인할 짧은 목록)
        │
        ├─ (사람이 실패 목록 검토 → 원본 수정 → 재실행)
        │
        ├─ scripts/import-members.mjs     (service_role 키로 쓰기)
        ▼
Supabase: members + member_pubg_accounts
```

**검증과 등록을 한 스크립트로 합치지 않는 이유**: 등록 단계에서 문제가 생겼을 때 API 호출을 처음부터 다시 하지 않아도 되고, 무엇보다 DB에 쓰기 전에 219줄을 눈으로 확인할 수 있다.

## 1단계: IGN 검증 (`scripts/verify-pubg-igns.mjs`)

옮겨 적은 IGN이 실제로 존재하는지 PUBG API로 확인하고, 동시에 `pubg_account_id`를 확보한다.

```
GET /shards/kakao/players?filter[playerNames]=<최대 10개, 쉼표 구분>
```

**이 단계가 판독 오류의 안전망이다.** 스크린샷에서 글자를 옮겨 적을 때 `0`/`O`, `1`/`l`/`I` 같은 문자를 잘못 읽을 수 있는데, PUBG 닉네임은 대소문자까지 구분하므로 틀리면 조회에 실패한다. 즉 API가 정답지 역할을 한다. 판독이 애매한 23건은 원본 `note`에 대안 IGN을 적어뒀고, 대안까지 함께 조회해서 실제로 존재하는 쪽을 채택한다.

**구현 시 주의할 점**:

- **속도 제한**: Players 엔드포인트는 분당 10회다. 219명을 10명씩 묶으면 22회, 대안까지 포함해도 25회 내외다. 6초 간격이면 약 3분이면 끝난다.
- **부분 성공 처리**: 배치 10개 중 일부만 존재할 때 API가 어떻게 응답하는지 실측한 적이 없다(부분 성공인지 전체 404인지). 따라서 **요청한 이름과 응답에 돌아온 이름을 대조**하고, 누락된 이름은 개별로 한 번 더 조회해서 확실히 판정한다.
- **재실행 가능**: 이미 `verified-igns.tsv`에 있는 이름은 건너뛴다. 중간에 끊겨도 이어서 돌릴 수 있어야 한다.
- **양쪽 다 존재하는 경우**: 대안까지 둘 다 실제로 존재하면 자동 판정하지 않고 실패 목록으로 빼서 사람이 고른다. 엉뚱한 사람의 계정을 연결하는 것이 미확인으로 남기는 것보다 나쁘다.

출력 `verified-igns.tsv`는 원본 컬럼에 `pubg_account_id`와 API가 돌려준 정확한 표기의 `pubg_ign`을 더한 것이다.

## 2단계: 스키마 변경 (`supabase/migrations/0003_member_identity.sql`)

### 왜 필요한가

현재 `members`에는 `discord_nickname` 하나뿐이고 여기에 유일성 제약이 걸려 있다. 실제 데이터를 보니 이 필드가 **식별 키와 표시 이름을 겸하는 것이 문제**다:

- 별명은 사람들이 수시로 바꾼다
- 별명은 유일성이 보장되지 않는다 (219명 중엔 중복이 없지만 우연이다)
- 디스코드 사용자명은 디스코드가 전역 유일성을 보장하고 거의 바뀌지 않는다

그래서 둘을 분리한다:

| 컬럼 | 예시 | 역할 |
|---|---|---|
| `discord_username` | `dlrpajsep` | 안정적인 식별 키 (유일성 제약) |
| `discord_nickname` | `Ez_LaPaz(현석/94)` | 관리자가 사람을 알아보는 표시용 (제약 없음) |

**지금 하는 이유**: 스크린샷 219명분을 이미 옮겨놨다. 나중에 필요해지면 이 수작업을 처음부터 다시 해야 한다. 그리고 향후 "클랜원이 디스코드 로그인해서 본인 부계정을 병합"하는 기능은 로그인이 돌려주는 값이 결국 사용자명이라, 이 컬럼 없이는 붙일 수 없다.

### 마이그레이션

Phase 1의 교훈대로 이미 적용된 `0001`/`0002`는 건드리지 않고 새 파일을 추가한다. 멱등하게 작성한다.

```sql
alter table members add column if not exists discord_username text;

-- 별명이 아니라 사용자명을 유일 키로 삼는다.
-- Postgres 유일 인덱스는 NULL 중복을 허용하므로, 기존 2행이 비어 있는 상태에서도 바로 걸 수 있다.
create unique index if not exists members_clan_discord_username_key
  on members (clan_id, discord_username);

-- 별명은 바뀌고 중복될 수 있으므로 유일성 제약을 뗀다.
alter table members drop constraint if exists members_clan_id_discord_nickname_key;

-- 티어 값이 0~5의 0.5 단위라는 것이 실제 데이터로 확인되었다.
-- Table Editor에서 손으로 고칠 때 오타를 막는다.
alter table members drop constraint if exists members_tier_valid;
alter table members add constraint members_tier_valid
  check (tier in (0, 1, 1.5, 2, 2.5, 3, 3.5, 4, 4.5, 5));
```

`청정수` 역할은 티어 5.0으로 저장한다. 기존 `numeric(3,1)` 컬럼이 그대로 수용하므로 타입 변경은 없다. 대시보드에서 "5티어"가 아니라 "청정수"로 보여야 한다면 표시 계층에서 처리한다.

이 마이그레이션은 Phase 1과 마찬가지로 **사람이 Supabase SQL Editor에 직접 붙여넣어 적용**한다(브라우저 조작이라 에이전트가 할 수 없다).

## 3단계: 등록 (`scripts/import-members.mjs`)

### 기존 데이터와 충돌하지 않게

`Ez_Code`와 `Ez_sejin`은 Phase 1에서 이미 등록돼 있고 `discord_username`이 비어 있다. 그냥 삽입하면 같은 사람이 두 번 들어가고, `member_pubg_accounts`의 `unique(pubg_ign)`에 걸려 실패한다.

**사람을 찾는 기준을 IGN으로 잡는다.** `member_pubg_accounts.pubg_ign`에는 이미 유일 제약이 있어 정확히 매칭된다.

```
verified-igns.tsv 한 줄마다:
  이 pubg_ign이 member_pubg_accounts에 이미 있는가?
    있다 → 그 member_id가 이 사람이다
           → members 갱신 (discord_username, discord_nickname, tier, updated_at)
           → member_pubg_accounts 갱신 (pubg_account_id)
    없다 → members에 삽입 (clan_id, discord_username, discord_nickname, tier, is_active=true)
           → member_pubg_accounts에 삽입 (member_id, pubg_ign, pubg_account_id)
```

이 방식이면 `Ez_Code`는 기존 행이 갱신되고, **부계정 `Ez_Codu`는 TSV에 없으므로 아무 영향도 받지 않고 그대로 남는다.** 스크립트를 여러 번 돌려도 결과가 같다.

`clan_id`는 `clans` 테이블에서 조회한다. 클랜이 0개거나 2개 이상이면 어느 클랜에 넣을지 알 수 없으므로 즉시 실패시킨다.

### 쓰기 권한

RLS가 INSERT/UPDATE를 막고 있으므로 `anon` 키로는 쓸 수 없다. RLS를 우회하는 `service_role` 키가 필요하다.

- 이 키는 사람이 Supabase 대시보드에서 복사해 `.env.local`에 넣어야 한다(브라우저 조작).
- **이 키는 모든 RLS를 우회한다.** 프론트엔드 코드나 git에 절대 들어가면 안 된다. `.env.local`은 이미 gitignore돼 있다.
- 서버에서 실행하는 스크립트에서만 쓴다. Phase 2의 폴링 함수도 같은 키를 쓰게 된다.

## 검증

등록 후 다음을 확인한다. 확인이 아니라 **자동 검사**로 만들어서, 조건이 깨지면 스크립트가 실패(exit 1)하게 한다 — Phase 1 리뷰에서 "검증 스크립트가 정작 검증해야 할 상황에서 실패하지 못했다"는 지적을 받았던 것과 같은 실수를 반복하지 않는다.

- `members` 행 수가 219와 일치한다
- 티어별 인원 분포가 위 표와 일치한다
- 모든 `members` 행에 `discord_username`이 채워져 있다
- 모든 `member_pubg_accounts` 행에 `pubg_account_id`가 채워져 있다
- `Ez_Code`가 여전히 IGN 두 개(`Ez_Code`, `Ez_Codu`)를 갖고 있다 — 기존 데이터를 깨뜨리지 않았다는 증거
- 스크립트를 두 번 실행해도 행 수가 늘지 않는다 (멱등성)

마이그레이션에서 하나 더 확인할 것이 있다. `drop constraint if exists members_clan_id_discord_nickname_key`는 이름이 틀려도 조용히 넘어간다 — Postgres가 자동 생성한 제약 이름이 실제로 이것인지 적용 전에 확인해야 한다. 안 그러면 제약이 안 떨어진 채로 남아, 나중에 누군가 별명을 남의 것과 같게 바꿀 때 영문 모를 오류를 만난다.

## 폴링(Phase 2)과의 관계

이 작업은 매치 폴링의 **선행 조건이 아니다.** Phase 2 설계에서 이미 정한 대로, 매치 응답에는 참가자 64명 전원의 accountId와 닉네임이 들어 있어 "누가 참가했는지"는 폴링이 알아낸다. 등록되지 않은 참가자는 `member_id`를 비운 채로 저장해두고, 나중에 그 사람이 등록되는 순간 과거 기록까지 소급 연결된다.

따라서 두 작업은 순서에 관계없이 진행할 수 있다. 다만 이 등록을 먼저 끝내두면 폴링이 수집한 데이터가 처음부터 사람에게 붙으므로, 이쪽을 먼저 한다.

## 이번 범위가 아닌 것

- 티어 역할이 없는 나머지 클랜원(약 230명) 등록
- 부계정 병합 (관리자 도구든 본인 인증이든)
- 디스코드 봇/API 연동을 통한 명단 자동 동기화
- `/admin` 페이지 — 이후에도 Supabase Table Editor로 충분하다
- 신규 가입자 등록 절차 — 당분간 Table Editor에 직접 추가한다
