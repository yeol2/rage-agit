# 과거 내전 입력 — 설계

PUBG API 가 놓친 과거 내전을 dak.gg 화면에서 읽어 DB 에 채운다. 범위는 **dak.gg 에 남아 있는 내전 전부** — 07-26 의 빠진 2경기와, 6월 중순~08-09 사이 아직 없는 5~6회분이다.

## 왜 dak.gg 인가

- PUBG API 는 **플레이어의 매치 목록을 14일만** 준다. 그보다 오래된 내전은 matchId 를 알아낼 방법이 없다.
- 매치 데이터 자체는 matchId 만 있으면 14일이 지나도 열린다(실측: 14일 3시간 된 매치가 200). **그래서 matchId 만 구하면 공식 API 로 갈 수 있었지만, 그 경로는 막혔다** — 아래 참고.
- 관리자의 게임 결과창 스크린샷에는 순위와 킬뿐이다. dak.gg 에는 전 지표가 있다.

## dak.gg 조사 결과 (실측)

브라우저로 직접 확인했다. 확정된 사실이다.

### 얻을 수 있는 것

`상세` 버튼(`button.Match__button`) → `전체 순위` 탭(`button.tab__button`)을 누르면 **추가 네트워크 요청 없이** 참가자 전원의 지표가 DOM 에 나타난다. 데이터가 이미 페이지에 들어 있고 표시만 토글된다.

읽히는 항목: 팀 순위(`#1`, `#2`…), 닉네임, 주 무기, 킬, 헤드, 어시, 딜량, DBNO, 이동 거리, 저격, 생존.

**내전 하나에 참가자 아무나 한 명의 프로필이면 4경기가 다 있다.** 참가 인원이 4경기 내내 고정이기 때문이다.

### 얻을 수 없는 것

| | 상태 |
|---|---|
| **PUBG matchId** | 없음. 페이지의 UUID 는 dak.gg 자체 값이고 PUBG API 에 넣으면 404. 상세를 하나 더 열어도 새 UUID 가 생기지 않으므로 **매치 식별자조차 아니다.** |
| **경기 시각** | 없음. 날짜(`7월 26일`)까지만. 화면의 `27:06` 같은 값은 생존 시간이다. |
| **accountId** | 없음. 닉네임만. |
| 보존 기간 | 약 2개월. `Ez_Grim` 기준 6월 16일까지(40페이지가 마지막). **2025 년은 dak.gg 에도 없다.** |

### 지표 대조

| DB 컬럼 | PUBG API | dak.gg |
|---|---|---|
| `kills` `headshot_kills` `assists` `damage_dealt` `dbnos` | ✅ | ✅ |
| `longest_kill` | ✅ | ✅ (`저격`) |
| `time_survived` `win_place` `team_rank` | ✅ | ✅ |
| `walk_distance` / `ride_distance` | ✅ 분리 | ⚠️ 합계만 (`6.47km`) |
| `heals` `boosts` `revives` | ✅ | ❌ |
| `team_id` | ✅ | ❌ (순위만) |
| `matches.duration_seconds` | ✅ | ❌ |
| `matches.game_mode` / `match_type` | ✅ | ❌ (단, 내전은 항상 `squad`/`custom`) |

## 결정 사항

### 반자동 — 관리자가 열고 에이전트는 읽기만 한다

관리자가 참가자 한 명의 dak.gg 전적에서 그 내전 4경기의 `상세 → 전체 순위`를 **열어둔다.** 에이전트는 브라우저 도구로 DOM 만 읽는다. 클릭하지 않고, 페이지를 순회하지도 않는다.

dak.gg 가 클래스 이름 하나만 바꿔도 자동 클릭은 조용히 멈추는데, 그 사실을 데이터가 안 들어온 뒤에야 알게 된다. 읽기만 하면 실패가 그 자리에서 드러난다.

### 없는 지표는 NULL — 0 이 아니라

`0` 은 SQL 이 **진짜 관측값으로 취급**한다. `NULL` 은 집계 함수가 건너뛴다.

어떤 클랜원이 API 내전 10경기(회복 평균 6회), dak.gg 내전 10경기(회복 모름)를 뛰었다고 하자:

| | `AVG(heals)` | `COUNT(heals)` |
|---|---|---|
| 0 으로 채움 | **3.0** ← 틀림 | 20 ← 거짓 표본 수 |
| NULL 로 둠 | **6.0** ← 맞음 | **10** ← 아는 경기 수 |

`0` 은 평균을 조용히 절반으로 떨어뜨리고 아무도 모른다.

### 식별자는 내용으로 만든 지문

날짜 + 맵 + 참가자 전원의 (닉네임·킬)을 정렬해 해시한다.

```
pubg_match_id = 'dakgg:' + sha1('2026-07-19|Desert_Main|Ez_Grim:2,Ez_Qhrb:3,...').slice(0, 16)
```

**순번(`2026-07-19:3`)이 아니라 해시인 이유**: 순번은 넣는 순서에 의존한다. 나중에 그날 다른 경기를 하나 더 발견하면 번호가 밀려 같은 매치가 두 번 들어간다. 해시는 내용이 같으면 항상 같은 값이라 몇 번을 다시 넣어도 한 행이다.

### 시각은 지어내지 않는다

`matches.source` 로 출처를 구분하고, dak.gg 출처의 `played_at` 은 **자리표시자**로 둔다 — 그날 KST `20:00` + `order` 분(`2026-07-19T20:01:00+09:00`). 세션 묶기(`attachToSession` 이 KST 날짜를 본다)와 경기 순서 정렬에만 쓴다.

**화면에서는 `source='dakgg'` 매치의 시각을 감춘다.** `20:01` 을 보여주면 사실인 것처럼 읽힌다.

### 나머지 빈 칸을 채우는 방식

| 컬럼 | dak.gg 출처의 값 | 근거 |
|---|---|---|
| `team_id` | `team_rank` 를 그대로 | 한 경기 안에서 순위는 팀마다 유일하다. 지어낸 값이 아니라 그 경기 안에서만 유효한 팀 식별자다 |
| `game_mode` | `squad` | 내전은 항상 스쿼드다 |
| `match_type` | `custom` | 사설방이다 |
| `duration_seconds` | `null` | 모른다 |
| `walk_distance` / `ride_distance` | `null` | 합계만 알아서 쪼갤 수 없다. 합계는 `total_distance` 에 넣는다 |

### accountId 는 아는 만큼 붙인다

dak.gg 는 닉네임만 주지만, 우리는 이미 닉네임↔계정 대응표를 갖고 있다. `member_pubg_accounts` 는 `pubg_ign` 이 유니크고 `member_id` 와 `pubg_account_id` 를 함께 들고 있으니, 한 번 조회로 **둘 다** 꺼낸다.

계정 ID 를 붙이는 게 중요한 이유는 칸을 채워서가 아니다:

- `0005` 의 `unique (pubg_match_id, pubg_account_id)` 가 원래대로 중복을 막는다
- `scrim_session_summary` 가 참가자를 계정 ID 로 센다 (아래 참고)
- 개인 지표를 계정 ID 로 집계할 때 dak.gg 경기가 **API 경기와 같은 사람으로 합쳐진다**

붙는 것은 이 추론이다: "그 시점 그 닉네임을 쓰던 사람은 지금 그 닉네임으로 등록된 사람이다." `member_id` 를 붙일 때 이미 하고 있는 추론과 같은 것이라 새로 감수하는 위험은 없다.

전부 붙지는 않는다:

| 경우 | 결과 |
|---|---|
| 등록 클랜원, 닉네임 그대로 | 둘 다 붙는다 (대부분) |
| 등록했지만 `pubg_account_id` 가 비어 있음 | `member_id` 만 — `data/failed-igns.tsv` 의 사람들 |
| 그 사이 개명 | 둘 다 `null` |
| 미등록 참가자 (게스트·남의 클랜) | 둘 다 `null` — 매 경기 1~2명 |

개명한 사람은 `scripts/link-alt-account.mjs` 로 옛 닉네임을 별칭으로 넣은 뒤 `scripts/relink-participants.mjs` 를 돌리면 소급 연결된다. 검증 스크립트가 안 붙은 닉네임 목록을 뱉어 이걸 찾게 한다.

### 내전 판별은 기존 로직 그대로

`supabase/functions/_shared/matches.mjs` 의 `classifyMatch` 를 그대로 통과시킨다. 실측으로 우리 내전은 98%, 남의 모임은 23% 라 중간값이 없다. dak.gg 에서도 낯선 닉네임뿐인 남의 커스텀은 이 비율에서 걸러진다.

## 스키마 — 마이그레이션 `0008`

```sql
alter table matches
  add column if not exists source text not null default 'pubg_api';

alter table match_participants alter column heals drop not null;
alter table match_participants alter column boosts drop not null;
alter table match_participants alter column revives drop not null;
alter table match_participants alter column pubg_account_id drop not null;
alter table match_participants
  add column if not exists total_distance numeric;
```

- `source` — 기존 행은 `default` 로 전부 `'pubg_api'` 가 된다. dak.gg 는 `'dakgg'`
- `heals`·`boosts`·`revives` 만 `not null` 해제. dak.gg 에 있는 지표는 안 건드린다
- `pubg_account_id` 도 해제 — 닉네임을 못 알아본 참가자용 예외 경로다 (아래)
- `total_distance` 는 API 출처도 `walk + ride` 로 채운다(`backfill-sessions.mjs` 에 추가). 화면은 이 컬럼만 본다

`0005` 가 `match_participants` 의 `unique (pubg_match_id, pubg_account_id)` 로 중복을 막고 있었는데, `pubg_account_id` 가 `null` 이면 이 제약이 걸리지 않는다(NULL 은 서로 같지 않다). 그 경우의 중복은 **`(pubg_match_id, pubg_ign)` 유니크 인덱스**로 막는다:

```sql
create unique index if not exists match_participants_ign_uniq
  on match_participants (pubg_match_id, pubg_ign);
```

**부분 인덱스(`where pubg_account_id is null`)로 만들면 안 된다.** 처음에 그렇게 설계했다가 적재가 통째로 막혔다 — Postgres 가 부분 인덱스를 `ON CONFLICT` 대상으로 추론하려면 INSERT 문에 인덱스의 `WHERE` 절이 그대로 들어가야 하는데, PostgREST 의 upsert 는 그걸 표현할 방법이 없다. 전체 인덱스로 해도 잃는 것이 없다: 한 경기 안에서 닉네임은 사람마다 유일하고, 실제 데이터 648행에도 중복이 0건이었다.

### `scrim_session_summary` 도 고쳐야 한다

`0007` 의 뷰가 참가자를 이렇게 센다:

```sql
count(distinct p.pubg_account_id) as participant_count
```

`count(distinct)` 는 `NULL` 행을 통째로 뺀다. 지금까지는 API 가 항상 `playerId` 를 줘서 드러나지 않았지만, `NULL` 이 섞이면 "64명 내전"이 조용히 적게 나온다. 닉네임으로 대체한다:

```sql
count(distinct coalesce(p.pubg_account_id, p.pubg_ign)) as participant_count
```

새 컬럼(`source`, `total_distance`)은 `0004` 방침대로 `grant select` 를 명시한다.

## 중간 JSON — `data/dakgg-scrims/YYYY-MM-DD.json`

내전 하루가 파일 하나. 에이전트가 쓰고, 관리자가 열어보고, import 가 읽는다. 읽기와 적재를 나누면 파서가 틀렸을 때 파일만 고쳐 다시 돌릴 수 있고, 둘을 따로 테스트할 수 있다.

```json
{
  "scrimDate": "2026-07-19",
  "source": "dakgg",
  "readAt": "2026-08-10T12:00:00+09:00",
  "readFrom": "Ez_Grim",
  "matches": [
    { "order": 1, "map": "미라마",
      "participants": [
        { "ign": "Ez_Grim", "teamRank": 3, "kills": 2, "headshotKills": 1,
          "assists": 0, "damageDealt": 412, "dbnos": 3,
          "totalDistance": 6472, "longestKill": 187, "timeSurvived": 1626 }
      ] }
  ]
}
```

한글 맵 이름을 **그대로 둔다.** 변환은 import 가 한다 — 파일이 화면과 같아야 관리자가 눈으로 대조할 수 있다.

## 맵 매핑

| dak.gg | DB |
|---|---|
| 에란겔 | `Baltic_Main` |
| 미라마 | `Desert_Main` |
| 태이고 | `Tiger_Main` |
| 사녹 | `Savage_Main` |
| 데스턴 | `Kiki_Main` |
| 론도 | `Neon_Main` |
| 비켄디 | `DihorOtok_Main` |

표에 없는 이름이 나오면 **중단한다.** `null` 로 넘어가면 그 경기만 맵이 빈 채 조용히 들어간다.

(에란겔의 API 값은 `Erangel_Main` 이 아니라 `Baltic_Main` 이다. 틀리면 같은 맵이 두 이름으로 갈라진다.)

## import — `scripts/import-dakgg-scrims.mjs`

`data/dakgg-scrims/*.json` 을 읽어 넣는다. 여러 번 돌려도 결과가 같다(지문 upsert).

파서·변환·지문 계산은 `scripts/lib/dakgg.mjs` 에 순수 함수로 두고 단위 테스트한다. 네트워크와 DB 는 스크립트 쪽에만 있다.

각 경기마다:

1. 맵 이름을 변환한다 (실패 시 중단)
2. 닉네임 → `member_id` + `pubg_account_id`. **`member_pubg_accounts` 만 보면 안 된다** — 미등록 참가자(게스트·탈퇴자)는 거기 없지만 이미 저장된 API 매치에는 계정 ID 가 들어 있다. 두 곳을 다 보지 않으면 같은 사람이 계정 ID 있는 행과 없는 행으로 갈라져 세션 참가자 수가 부풀어 오른다 (07-26 을 넣었을 때 68명이 74명으로 나왔다)
3. `classifyMatch({ matchType: 'custom', participantCount, clanMemberCount })` — 내전이 아니면 건너뛰고 이유를 출력
4. **중복 가드** — 같은 날짜에 이미 있는 매치의 `(닉네임:킬)` 집합과 겹치면 넣지 않고 건너뛴다
5. 지문으로 `matches` upsert (`source='dakgg'`), 참가자 적재, `attachToSession` 으로 세션 연결

**중복 가드가 필요한 이유**: 07-26 은 API 로 넣은 2경기가 이미 있는데, 같은 경기를 dak.gg 에서 읽으면 지문이 PUBG matchId 와 달라 별개 행이 된다. 그러면 그날 경기 수와 참가자 통계가 두 배가 된다.

## 화면

- `source='dakgg'` 매치는 시각 대신 `1경기`·`2경기`
- `heals`/`boosts`/`revives` 가 `null` 이면 `—`
- 집계는 `AVG`/`SUM` 이 `NULL` 을 건너뛰므로 그대로 두면 맞다

## 검증

07-26 은 이미 API 데이터 2경기가 있고 dak.gg 에도 같은 2경기가 보인다. **두 출처가 같은 사람에게 같은 값을 주는지 대조할 수 있는 드문 기회다.**

1. 07-26 의 이미 있는 2경기를 dak.gg 에서도 읽어 JSON 으로 떨어뜨린다 → **import 하지 않고** DB 와 대조. 참가자 수, 사람별 킬·딜량·순위가 일치해야 한다. **여기서 안 맞으면 나머지는 안 넣는다**
2. 통과하면 나머지 내전(07-26 의 빠진 2경기 포함)을 적재
3. `scripts/verify-dakgg-import.mjs` — 세션별 경기 수, `source` 분포, `member_id` 가 안 붙은 닉네임 목록, 지문 중복 0건

## 범위 밖

**2025 년 게임 결과창 스크린샷.** 지표가 순위와 킬뿐이라 형태가 또 다르고, dak.gg 에도 남아 있지 않다. 별도 설계가 필요하다.
