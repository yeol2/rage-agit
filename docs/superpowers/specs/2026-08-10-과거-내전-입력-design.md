# 과거 내전 입력 — 설계 (작성 중)

> **상태: 브레인스토밍 도중 세션이 끝나 여기까지 정리해둔 것이다.** 조사 결과는 확정이고, "정해야 할 것" 절이 남은 논의다. 새 세션은 이 문서부터 읽고 이어가면 된다.

## 목표

PUBG API 가 놓친 과거 내전을 dak.gg 화면에서 읽어 DB 에 채운다. 범위는 **dak.gg 에 남아 있는 내전 전부** — 07-26 의 빠진 2경기와, 6월 중순~08-09 사이 아직 없는 5~6회분이다.

## 왜 dak.gg 인가

- PUBG API 는 **플레이어의 매치 목록을 14일만** 준다. 그보다 오래된 내전은 matchId 를 알아낼 방법이 없다.
- 매치 데이터 자체는 matchId 만 있으면 14일이 지나도 열린다(실측: 14일 3시간 된 매치가 200). **그래서 matchId 만 구하면 공식 API 로 갈 수 있었지만, 그 경로는 막혔다** — 아래 참고.
- 관리자의 게임 결과창 스크린샷에는 순위와 킬뿐이다. dak.gg 에는 전 지표가 있다.

## dak.gg 조사 결과 (실측)

브라우저로 직접 확인했다. 확정된 사실이다.

### 얻을 수 있는 것

`상세` 버튼(`button.Match__button`) → `전체 순위` 탭(`button.tab__button`)을 누르면 **추가 네트워크 요청 없이** 참가자 전원의 지표가 DOM 에 나타난다. 데이터가 이미 페이지에 들어 있고 표시만 토글된다.

읽히는 항목: 팀 순위(`#1`, `#2`…), 닉네임, 주 무기, 킬, 헤드, 어시, 딜량, DBNO, 이동 거리, 저격, 생존.

**내전 하나에 참가자 아무나 한 명의 프로필이면 4경기가 다 있다.** 참가 인원이 4경기 내내 고정이기 때문이다. 페이지 1개 + 클릭 4번이면 그 내전이 끝난다.

### 얻을 수 없는 것

| | 상태 |
|---|---|
| **PUBG matchId** | 없음. 페이지의 UUID 는 dak.gg 자체 값이고 PUBG API 에 넣으면 404. 상세를 하나 더 열어도 새 UUID 가 생기지 않으므로 **매치 식별자조차 아니다.** |
| **경기 시각** | 없음. 날짜(`7월 26일`)까지만. 화면의 `27:06` 같은 값은 생존 시간이다. |
| **accountId** | 없음. 닉네임만. |
| 보존 기간 | 약 2개월. `Ez_Grim` 기준 6월 16일까지(40페이지가 마지막). **2025 년은 dak.gg 에도 없다.** |

### 접근 방식

관리자가 **반자동**을 택했다 — 본인이 페이지를 열고 에이전트가 읽는다. 전자동 순회는 하지 않는다. dak.gg 가 클래스 이름 하나만 바꿔도 조용히 멈추는데, 그 사실을 데이터가 안 들어온 뒤에야 알게 되기 때문이다.

## 현재 스키마와 충돌하는 지점

- `matches.pubg_match_id` 가 기본키인데 **대체할 값이 없다**
- `matches.played_at` 이 타임스탬프인데 **날짜까지만 안다**
- `match_participants.pubg_account_id` 가 `not null` 인데 **닉네임만 있다**
- 같은 매치를 두 번 읽어도 **막을 자연키가 없다**

## 여기까지 제안한 해법

### 식별자는 내용으로 만든 지문

날짜 + 맵 + 참가자 전원의 (닉네임·킬)을 정렬해 해시한다.

```
pubg_match_id = 'dakgg:' + sha1('2026-07-26|Erangel_Main|Ez_Grim:2,Ez_Qhrb:3,...').slice(0, 16)
```

**순번(`2026-07-26:3`)이 아니라 해시인 이유**: 순번은 넣는 순서에 의존한다. 나중에 그날 다른 경기를 하나 더 발견하면 번호가 밀려 같은 매치가 두 번 들어간다. 해시는 내용이 같으면 항상 같은 값이라 몇 번을 다시 넣어도 한 행이다.

### 시각은 지어내지 않는다

`matches.source` 컬럼을 추가해 `'pubg_api'` / `'dakgg'` 를 구분한다. dak.gg 출처는 `played_at` 을 그날 순서만 보존하는 근사값으로 두고, **화면에서는 시각을 감춘다.** `20:30` 같은 지어낸 값을 보여주면 사실인 것처럼 읽힌다.

### accountId 는 nullable 로

닉네임으로 `member_pubg_accounts.pubg_ign` 을 찾아 `member_id` 를 붙인다. 개명한 사람은 안 붙지만 이미 있는 문제이고, `scripts/link-alt-account.mjs` 로 별칭을 넣은 뒤 `scripts/relink-participants.mjs` 를 돌리면 소급 연결된다.

### 내전 판별은 기존 로직 그대로

참가자 중 등록 클랜원 비율이 기준이다(`supabase/functions/_shared/matches.mjs` 의 `classifyMatch`). 실측으로 우리 내전은 98%, 남의 모임은 23% 라 중간값이 없다. dak.gg 에서도 낯선 닉네임뿐인 남의 커스텀은 이 비율에서 걸러진다.

## 아직 정하지 않은 것

1. **작업 흐름의 정확한 분담** — 관리자가 페이지만 열고 에이전트가 클릭까지 하는지, 아니면 `전체 순위`까지 열어두는지.
2. **중간 산물** — 읽은 것을 바로 DB 에 넣을지, `data/` 아래 JSON 으로 한 번 떨어뜨려 검토한 뒤 넣을지. (클랜원 등록 때는 중간 파일을 뒀고 그게 도움이 됐다.)
3. **맵 이름 매핑** — dak.gg 는 한글(`미라마`, `태이고`, `에란겔`)로 보여주고 우리 DB 는 API 값(`Desert_Main`, `Tiger_Main`, `Baltic_Main`)을 쓴다. 대응표가 필요하다.
4. **검증 기준** — 넣은 뒤 무엇을 확인해야 맞다고 할 수 있는가. 07-26 은 이미 2경기가 있으므로 **같은 날 기존 API 데이터와 새 dak.gg 데이터가 나란히 놓인다** — 두 출처가 같은 사람에게 같은 값을 주는지 대조할 수 있는 드문 기회다.
5. **2025 년 게임 결과창 스크린샷** — 이번 범위 밖으로 미뤘다. 지표가 순위와 킬뿐이라 형태가 또 다르다.
