# 매치 폴링 파이프라인 — 설계

> [빅뱅배포.md](../빅뱅배포.md)의 API 연동 4단계 중 2단계.
> 1단계(클랜원 등록)는 [스키마 설계](../sessions/2026-08-09-클랜원등록/클랜원등록.md)와 [일괄 등록](2026-08-09-클랜원-일괄등록-design.md)으로 끝났고, 현재 214명이 등록돼 있다.

## 목적

내전이 열리면 그 기록을 PUBG API에서 가져와 우리 DB에 쌓는다. **PUBG API는 최근 14일치만 제공하므로**(실측 확인), 주기적으로 가져와 두지 않으면 지난 내전은 영영 복구할 수 없다.

이번 범위는 **내전 데이터를 수집해 저장하는 것까지**다. 대시보드 연동(4단계)은 다루지 않는다.

## 실측으로 확인된 사실

설계의 근거가 된 값들이다. 모두 실제 API 응답에서 확인했다.

### 관전 계정은 쓸 수 없다

`Ez_Rage-`가 모든 내전에 관전으로 들어간다고 해서, 그 계정 하나만 조회하면 되는지 확인했다. **안 된다** — 최근 매치 174개가 전부 `competitive`이고 커스텀은 0개였다. 같은 기간 `Ez_Code`에게는 커스텀 9경기가 잡혔으므로 내전은 분명히 있었다. 관전 슬롯은 참가자로 기록되지 않아 그 사람의 매치 목록에 아예 올라오지 않는다.

따라서 matchId는 **실제로 뛴 클랜원을 통해서만** 얻을 수 있다.

### 보존 기간은 정확히 14일

`Ez_Rage-`의 목록에서 가장 오래된 매치가 조회 시점(08-09)으로부터 14일 전인 07-26이었다.

### `custom` 만으로는 우리 내전을 특정할 수 없다

`Ez_Code`의 커스텀 9경기가 두 날에 걸쳐 있었는데, 관리자 확인 결과 **07-31 5경기는 우리 내전이 아니었다**(다른 모임에 클랜원 일부가 낀 것). 그런데 두 날의 겉모습이 완전히 같다:

| | 07-31 (내전 아님) | 08-02 (내전) |
|---|---|---|
| `matchType` | `custom` | `custom` |
| `gameMode` | `esports-squad` | `esports-squad` |
| 참가자 / 팀 | 64명 / 16팀 | 64명 / 16팀 |
| **등록 클랜원** | **15명 (23%)** | **63명 (98%)** |

**판별력이 있는 값은 등록 클랜원 비율 하나뿐이다.** 23% 대 98%로 중간값이 없다.

참가자 수는 판별에 쓸 수 없다. 내전 인원은 50~70명으로 변동하며 64명 고정이 아니다.

### 한 번 정해진 인원이 그날 4매치를 함께 뛴다

그날 참가 인원(50~70명)이 1~4매치 동안 그대로 유지된다. 3단계(내전 세션 묶기)에서 시간 군집화를 보강할 신호로 쓸 수 있다.

## 파이프라인

```
scripts/poll-matches.mjs   (직접 실행. 검증 후 Edge Function 으로 이식한다)
   │
   ├─ 1. 씨앗 선정 — 누구의 매치 목록을 볼 것인가
   │
   ├─ 2. Players API 로 그들의 최근 matchId 수집 → 중복 제거
   │
   ├─ 3. DB 에 없는 matchId 만 Matches API 로 조회
   │
   ├─ 4. 내전 판별 — 등록 클랜원 비율
   │
   └─ 5. 저장 + 미등록 참가자 리포트
```

### 1. 씨앗 선정

최근 30일 내전에 자주 나온 클랜원 상위 20명을 조회 대상으로 삼는다.

```sql
select member_id, count(*) as attendance
from match_participants p join matches m using (pubg_match_id)
where m.played_at >= now() - interval '30 days' and p.member_id is not null
group by member_id order by attendance desc limit 20;
```

참가 기록이 없는 첫 실행에서는 **사람이 씨앗을 지정한다** (`--seed=Ez_Code`). 한 번이라도 내전을 수집하고 나면 그 참가자들이 다음 실행의 씨앗이 되므로, 이후로는 2회 호출에 수십 초로 끝난다.

**첫 실행에 전원을 훑지 않는 이유**: 등록된 214명의 최근 14일 매치를 합치면 수천 건이 되고, 어떤 매치인지는 열어봐야 알기 때문에 10분 이상 걸린다. 그런데 최근 내전에 나온 사람 한 명만 알면 몇 초에 끝난다 — 그 사람의 매치 목록에 내전 4경기가 전부 들어 있다. 반대로 아무나 몇 명 골라 넣으면 그들이 안 나온 내전을 조용히 놓친다. 어느 쪽도 자동으로 정할 수 없으므로 사람에게 묻고, 인자 없이 실행하면 안내와 함께 멈춘다(`--seed-all`로 전원 훑기를 강제할 수는 있다).

**씨앗 명단을 사람이 관리하지 않는 것이 핵심이다.** 손으로 정해두면 그 사람들이 탈퇴하거나 한동안 안 나올 때 조용히 망가진다. 참가 기록에서 뽑으면 클랜 구성이 바뀌어도 따라간다.

내전 참가 인원이 50~70명이고 등록 인원이 214명이므로, 상위 20명 중 아무도 참석하지 않을 확률은 무시할 만하다. 설령 놓치더라도 다음 날 실행에서 잡힌다 — 14일 안에만 발견하면 된다.

### 2~3. 매치 수집

Players 엔드포인트는 **분당 10회 제한**이고 한 번에 10명까지 조회한다. Matches 엔드포인트는 **속도 제한이 없다**(실측).

씨앗 20명의 매치 목록을 합치면 같은 내전 matchId 가 여러 번 나온다. 중복을 제거하고, `matches` 테이블에 이미 있는 것은 조회조차 하지 않는다.

### 4. 내전 판별

```
내전이다  ⟺  matchType == 'custom'
          AND 참가자 40명 이상
          AND 등록 클랜원 비율 ≥ 50%
```

실측값이 23% 대 98%라 50%는 양쪽 어디서도 멀다.

**참가자 40명 조건이 필요한 이유**: 클랜원 4명이 사설방에서 연습하면 비율은 100%지만 내전이 아니다. 내전 인원이 50~70명이라 40은 여유 있는 바닥값이다.

"등록 클랜원"은 참가자의 `playerId`(accountId)가 `member_pubg_accounts.pubg_account_id` 에 있는지로 판정한다. 닉네임이 아니라 accountId 로 맞추는 이유는, 사람들이 게임 내 닉네임을 바꾸기 때문이다(1단계에서 실제로 여러 건 확인됐다).

판별에서 탈락한 매치는 저장하지 않는다.

### 5. 저장과 리포트

매치와 참가자를 저장하고, **등록되지 않은 참가자를 따로 출력한다.**

이 리포트는 부가 기능이 아니라 **명단을 고치는 주된 수단이다.** 실제로 08-02 내전의 미등록 참가자 7명을 살펴본 결과, 아무도 외부인이 아니었다:

| 미등록 참가자 | 정체 |
|---|---|
| `Ez_time-`, `Ez_2pan4pan_` | 1단계에서 IGN 을 못 찾았던 사람 — 이걸로 찾음 |
| `Ez_Xavi-`, `Ez_ZiDe_` | 1단계가 **엉뚱한 계정**에 연결해둔 사람 |
| `Ez_Coldu`, `Ez_Juhyunping` | 등록된 클랜원의 부계정 |
| `Ez_HxxJxx` | 미확인 (보류) |

이 중 `Ez_HxxJxx` 를 뺀 나머지는 설계 단계에서 이미 명단에 반영했다. 그래서 위 표의 "등록 클랜원 63명(98%)"은 반영 후 기준이고, 처음 조회했을 때는 57명(89%)이었다. 어느 쪽이든 23% 와는 한참 떨어져 있다.

특히 `Ez_Xavi-`의 경우, 1단계 검증은 `Ez_XAVl`(끝이 소문자 L)이라는 **실존하는 남의 계정**을 물어 통과해버렸다. "그 이름의 플레이어가 존재한다"는 약한 신호이고, **"우리 내전에 실제로 뛰었다"가 훨씬 강한 신호**다. 이 리포트를 통해 명단은 내전이 열릴 때마다 스스로 정확해진다.

## 스키마

`supabase/migrations/0005_match_polling.sql` 로 추가한다. 0001~0004 는 건드리지 않는다.

```sql
create table if not exists matches (
  pubg_match_id text primary key,          -- PUBG 의 matchId 를 그대로 키로 쓴다
  played_at timestamptz not null,          -- 응답의 createdAt
  match_type text not null,                -- 'custom'
  game_mode text not null,                 -- 'esports-squad'
  map_name text,
  duration_seconds integer,
  participant_count integer not null,      -- 판별 근거
  clan_member_count integer not null,      -- 판별 근거
  raw_attributes jsonb not null,
  polled_at timestamptz not null default now()
);

create table if not exists match_participants (
  id uuid primary key default gen_random_uuid(),
  pubg_match_id text not null references matches(pubg_match_id) on delete cascade,
  member_id uuid references members(id),   -- 비어 있을 수 있다 (미등록 참가자)
  pubg_account_id text not null,
  pubg_ign text not null,                  -- 그 경기 당시 닉네임
  team_id integer not null,
  team_rank integer not null,              -- 팀 순위 1~16
  kills integer not null,
  assists integer not null,
  damage_dealt numeric not null,
  dbnos integer not null,
  headshot_kills integer not null,
  win_place integer not null,
  time_survived numeric not null,
  heals integer not null,
  boosts integer not null,
  longest_kill numeric not null,
  revives integer not null,
  raw_stats jsonb not null,
  unique (pubg_match_id, pubg_account_id)
);

create index if not exists match_participants_member_idx
  on match_participants (member_id);
create index if not exists matches_played_at_idx
  on matches (played_at desc);
```

### 왜 `pubg_match_id` 를 그대로 기본키로 쓰는가

매치는 이미 전역 유일한 ID 를 갖고 있어 별도 키를 만들 이유가 없다. 그리고 이것이 그대로 **중복 방지 장치**가 된다 — 폴링이 하루에 여러 번 돌아도 같은 매치가 두 번 들어가지 않는다.

### 왜 참가자를 64명 전원 저장하는가

브레인스토밍 초반에는 "우리 클랜원만 저장"으로 정했다가 바꿨다. 위에서 보듯 **미등록 참가자는 외부인이 아니라 명단이 틀린 우리 클랜원**이었다. 이들을 저장하지 않으면 나중에 명단을 고쳐도 그날 기록이 없다. `member_id` 를 비워 저장해두면 **명단을 고치는 순간 과거 경기까지 자동으로 연결된다.** 매치당 몇 행 더 넣는 것이 전부다.

### 왜 판별 근거를 컬럼으로 남기는가

`participant_count` 와 `clan_member_count` 가 있으면 "이 매치가 왜 내전으로 잡혔는가"를 나중에 되짚을 수 있다. 임계값을 조정하더라도 재수집 없이 과거 판정을 다시 계산할 수 있다 — 14일이 지나면 재수집이 불가능하므로 이게 중요하다.

### 왜 팀 테이블을 따로 만들지 않는가

팀은 그 경기에만 존재하고, 팀 순위는 그 팀 소속 참가자 모두에게 같은 값이다. `team_id`/`team_rank` 두 컬럼으로 충분하며, 조인 없이 "이 사람이 몇 등 했나"를 읽을 수 있다.

### 권한

읽기는 공개(대시보드가 공개 페이지다), 쓰기는 막는다. `0004` 에서 정한 방침대로 **컬럼을 명시적으로 열어준다** — 새 컬럼이 실수로 공개되는 것을 막는다.

```sql
alter table matches enable row level security;
alter table match_participants enable row level security;

drop policy if exists "matches_select_public" on matches;
create policy "matches_select_public" on matches for select using (true);

drop policy if exists "match_participants_select_public" on match_participants;
create policy "match_participants_select_public" on match_participants for select using (true);

-- raw_attributes / raw_stats 는 공개할 이유가 없다. 참가자 전원의 원본 스탯이 들어 있다.
revoke select on matches from anon, authenticated;
grant select (pubg_match_id, played_at, match_type, game_mode, map_name,
              duration_seconds, participant_count, clan_member_count, polled_at)
  on matches to anon, authenticated;

revoke select on match_participants from anon, authenticated;
grant select (id, pubg_match_id, member_id, pubg_ign, team_id, team_rank,
              kills, assists, damage_dealt, dbnos, headshot_kills,
              win_place, time_survived, heals, boosts, longest_kill, revives)
  on match_participants to anon, authenticated;
```

`pubg_account_id` 도 공개하지 않는다 — 대시보드가 쓸 일이 없고, 계정 식별자를 굳이 내보낼 이유가 없다.

## 실행 환경

이번에는 **로컬 스크립트**(`scripts/poll-matches.mjs`)로 만들고, Edge Function 이식은 다음 단계로 미룬다.

원래 계획은 Supabase Edge Functions + pg_cron 이었다. 그것이 최종 형태인 것은 변함없다 — **로컬 스크립트만으로는 "매일 자동"이 성립하지 않기 때문이다.** PC 가 꺼져 있거나 실행을 잊으면 14일이 지나 데이터가 사라진다.

그럼에도 로컬을 먼저 만드는 이유:

- **08-02 내전 4경기가 08-16 에 사라진다.** 로컬 스크립트는 오늘 안에 만들어 돌릴 수 있지만, Edge Function 은 CLI 설치·인증·배포 설정까지 며칠이 걸릴 수 있다.
- 판별 임계값을 실데이터로 조정해야 하는데, 로컬이 훨씬 빠르다.
- 1단계에서 만든 `scripts/lib/` 를 그대로 쓸 수 있다.
- Edge Function 은 Deno 라 런타임이 다르다. 로직이 검증되지 않은 상태에서 환경 차이까지 겹치면 원인을 가리기 어렵다.

**이식은 이번 범위가 아니지만 미루는 것이지 취소가 아니다.** 그때까지는 내전 다음 날 직접 실행해야 한다.

## 실패해도 멈추지 않게

- **속도 제한(429)** — 60초 대기 후 재시도. 1단계 검증 스크립트에서 검증된 방식이다.
- **매치 하나 조회 실패** — 그 매치만 건너뛰고 나머지는 계속한다. 4경기 중 1경기가 실패해도 3경기는 저장된다.
- **재실행 안전** — 이미 저장된 매치는 조회하지 않는다. 몇 번을 다시 돌려도 결과가 같다.
- 부분적으로 실패해도 성공한 것은 저장하고, 실패 건수를 마지막에 보고한다.

## 검증

### 자동 테스트 (vitest)

순수 로직만 다룬다. 픽스처는 실제 응답을 본떠 **작게 손으로 만든다** — 64명짜리 실제 응답을 저장소에 넣으면 클랜원 실명이 git 에 들어간다(명단 TSV 를 gitignore 한 것과 같은 이유).

- 내전 판별: 비율 98%/64명 → 내전, 23%/64명 → 아님, 100%/4명 → 아님(참가자 부족), `competitive` → 아님
- 매치 응답에서 참가자 추출: roster 의 `rank` 가 소속 참가자 전원의 `team_rank` 로 들어가는가
- accountId 로 `member_id` 를 붙이는가, 없으면 비워두는가

### 실데이터 검증

08-02 4경기로 확인한다. 기대값이 이미 확정돼 있다:

- 4경기가 내전으로 판정된다
- **07-31 5경기는 탈락한다** (같은 겉모습을 가진 남의 모임)
- 각 매치에 참가자 64명, 그중 `member_id` 연결이 63명
- 미등록 1명은 `Ez_HxxJxx`
- **스크린샷의 1등 팀 구성원과 DB 의 `team_rank = 1` 인 참가자가 일치한다**

마지막 항목이 특히 중요하다. 나머지는 전부 API 응답을 API 로 검산하는 것이라, 우리가 응답을 통째로 잘못 해석하고 있어도 통과한다. **사람이 게임 화면에서 본 결과와 대조하는 유일한 지점**이다.

## 이번 범위가 아닌 것

- **Edge Function 이식과 pg_cron 스케줄** — 다음 단계. 그때까지는 직접 실행한다.
- **과거 내전 스크린샷 입력** — 관리자가 2025~2026 내전 결과 스크린샷을 갖고 있다. 별도 세션으로 다룬다. 스크린샷에는 팀 순위와 개인 킬만 있고 데미지·생존시간·accountId 가 없어 데이터 형태가 다르고, 옛 닉네임을 현재 명단에 붙이는 문제도 따로 풀어야 한다. 스크린샷은 사라지지 않으므로 급하지 않다.
- **내전 세션 묶기** — 같은 날 4경기를 하나의 "내전"으로 묶는 것은 3단계다. 이번에는 매치 단위로만 저장한다.
- **대시보드 연동** — 4단계.
- **경쟁전 수집** — 내전만 저장한다. 나중에 필요해지면 씨앗 범위를 214명 전원으로 넓히고 판별 조건을 완화하면 된다.
- **텔레메트리** — 매치당 별도 요청이 필요하고 용량이 크다. 지금 쓸 데가 없다.
