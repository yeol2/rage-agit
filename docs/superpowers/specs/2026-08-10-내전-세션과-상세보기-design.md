# 내전 세션 묶기와 상세 보기 — 설계

> [빅뱅배포.md](../빅뱅배포.md)의 API 연동 4단계 중 **3단계(내전 세션 묶기)**와, 4단계(대시보드 연동) 중 내전 목록 부분을 함께 다룬다.

## 왜 둘을 같이 하는가

3단계는 "같은 날 4경기를 하나의 내전으로 묶는 것"이다. 그런데 묶기만 하고 보여주지 않으면 제대로 묶였는지 알 수 없다. 관리자가 원하는 화면 — **내전 칸을 펼치면 매치 1~4, 또 펼치면 선수별 지표** — 에서 "내전 칸"이 곧 세션이므로, 세션 없이는 화면이 성립하지 않고 화면 없이는 세션을 검증할 수 없다.

그래서 하나로 묶는다. 대신 **티어 랭킹 포디움은 목업으로 남긴다** — 거기 필요한 `score` 를 무엇으로 계산할지는 아직 아무데도 정해진 바가 없고, 그 자체로 별도 설계가 필요한 주제다.

## 현재 가진 데이터

| 날짜 | 경기 | 참가자 | 클랜원 인식 |
|---|---|---|---|
| 2026-07-26 | 2 | 68명 | 65 |
| 2026-08-02 | 4 | 64명 | 63 |
| 2026-08-09 | 4 | 64명 | 64 |

07-26 이 2경기뿐인 것은 폴링을 만들기 전에 나머지 2경기가 이미 API 목록에서 사라졌기 때문이다. **PUBG API 로는 복구할 수 없다** — matchId 를 알아낼 경로가 없다(dak.gg 는 PUBG matchId 를 노출하지 않는다). 관리자가 dak.gg 스크린샷으로 채우기로 했고, 그건 과거 내전 입력 세션에서 다룬다.

앞으로는 폴링이 주 2회 자동으로 돌므로 같은 유실이 생기지 않는다.

## 데이터 계층

### 세션 테이블

```sql
create table if not exists scrim_sessions (
  id uuid primary key default gen_random_uuid(),
  clan_id uuid not null references clans(id),
  scrim_date date not null,              -- 한국시간 기준 날짜
  title text not null,                   -- '2026-08-09 (일) 내전'
  session_number integer,                -- 비워둔다. 과거 내전을 넣은 뒤 채운다
  replay_url text,                       -- 관리자가 넣는다. API 에 없다
  created_at timestamptz not null default now(),
  unique (clan_id, scrim_date)
);

alter table matches add column if not exists scrim_session_id uuid references scrim_sessions(id);
create index if not exists matches_session_idx on matches (scrim_session_id);
```

**묶는 기준은 한국시간 날짜다.** 매치는 UTC 로 저장되지만 내전은 한국시간 저녁 8시~9시 40분에 열려서(실측: 08-02 기준 20:01~21:39), 사람이 "8월 9일 내전"이라고 부르는 것과 맞추려면 KST 기준이어야 한다.

`session_number` 를 지금 만들어두는 이유: 관리자가 과거 내전을 넣은 뒤 `#1`, `#2` 를 붙이겠다고 했다. 비어 있는 컬럼 하나를 미리 두면 그때 마이그레이션을 또 하지 않아도 된다.

### 경기 수와 참가 인원은 저장하지 않는다

```sql
create or replace view scrim_session_summary as
select s.id, s.clan_id, s.scrim_date, s.title, s.session_number, s.replay_url,
       count(distinct m.pubg_match_id) as match_count,
       count(distinct p.pubg_account_id) as participant_count,
       min(m.played_at) as started_at
from scrim_sessions s
left join matches m on m.scrim_session_id = s.id
left join match_participants p on p.pubg_match_id = m.pubg_match_id
group by s.id;
```

**왜 유도하는가**: 하루 4경기가 항상 한 번의 폴링에 다 들어오지 않는다. 실제로 그런 일이 있었다 — 08-09 첫 수집에서 3경기만 잡혔고 마지막 경기(12:38 시작)는 아직 끝나지 않아 API 에 없었다. 나중 실행에서 4번째가 붙었다.

숫자를 컬럼에 저장해두면 매치가 뒤늦게 붙을 때마다 다시 세야 하고, 한 번 빠뜨리면 조용히 틀린 값이 남는다. 뷰로 두면 **항상 실제 데이터와 일치**한다.

### 세션은 폴링이 만든다

내전을 저장할 때 그 매치의 KST 날짜로 세션을 찾고, 없으면 만들고, `matches.scrim_session_id` 에 붙인다.

```
내전 매치 저장
  → KST 날짜 계산 (played_at + 9시간)
  → 그 날짜 세션이 있나?
       있다 → 그 세션에 붙인다
       없다 → 만들고 붙인다 (제목: '2026-08-09 (일) 내전')
```

이미 저장된 10경기는 `scripts/backfill-sessions.mjs` 로 한 번 소급해 묶는다.

관리자가 손댈 것은 **다시보기 URL 뿐**이다. Table Editor 에서 `replay_url` 을 채운다. 제목이 마음에 안 들면 거기서 고칠 수 있다 — 자동 생성은 만들 때 한 번뿐이고 이후에는 건드리지 않는다.

### 권한

`0004` 에서 정한 방침대로 컬럼을 명시적으로 연다. 세션은 대시보드가 통째로 쓰는 정보라 사실상 전부 열지만, 앞으로 컬럼이 추가될 때 실수로 공개되지 않도록 명시한다.

## 화면

### 읽기는 브라우저에서 Supabase 로 직접 한다

별도 API 라우트를 만들지 않는다. `anon` 키는 공개돼도 되는 값이고, `0004`/`0005` 에서 **컬럼 단위로 이미 잠가놨다** — `raw_stats`, `raw_attributes`, `pubg_account_id`, `discord_username` 은 애초에 읽히지 않는다. 라우트를 하나 더 두면 그 잠금을 다시 구현하는 셈이고, 두 곳이 어긋날 여지만 생긴다.

### 펼칠 때 가져온다

```
첫 로드 (서버)      내전 목록만 — scrim_session_summary
   │
펼치면 (브라우저)    그 세션의 매치들 — 맵·시각·우승 팀
   │
또 펼치면 (브라우저)  그 매치의 참가자 — 순위·팀·킬·어시·딜량·DBNO·헤드샷·생존·이동거리
```

지금은 내전 3회라 전부 보내도 되지만, 주 2회면 1년에 100회가 쌓인다. 100회 × 4경기 × 64명 = **25,600행**이 첫 화면에 실릴 수는 없다. 펼칠 때만 가져오면 내전이 몇 백 회로 늘어도 첫 화면은 그대로다.

### 화면 모양

```
▸ 2026-08-09 (일) 내전          64명 · 4경기        [다시보기]
▸ 2026-08-02 (일) 내전          64명 · 4경기        [준비중]
▾ 2026-07-26 (일) 내전          68명 · 2경기        [준비중]
     ▸ 1경기  21:20  미라마     우승 12팀
     ▾ 2경기  21:54  태이고     우승 7팀
          순위  팀   닉네임          킬  어시  딜량  DBNO  헤드  생존    이동
          1     7    Ez_Vss-        3   1     412   2     1     24:32  6.5km
          ...
```

**저격거리는 넣지 않는다.** dak.gg 에는 있지만 클랜 내전에서 볼 이유가 없고, 열이 하나 늘면 좁은 화면에서 표가 먼저 깨진다.

**기존 `RecentScrimsList` 를 고친다.** 새 컴포넌트를 만들지 않는 이유는, 그 목록이 이미 내전 칸을 그리고 있고 필요한 것은 거기에 펼치기가 붙는 것뿐이기 때문이다.

**참가자는 팀 순위로 묶어 정렬한다** — 1등 팀 4명, 2등 팀 4명 순. dak.gg 의 "전체 순위" 탭과 같은 배열이고, 관리자가 그 화면과 대조하기 쉽다.

**클랜원으로 인식된 사람은 디스코드 별명을 함께 보여준다.** `member_id` 가 붙은 참가자는 누구인지 알기 때문이다. 안 붙은 사람은 IGN 만 나오므로, **화면에서도 "명단에 없는 사람"이 눈에 띈다** — 폴링의 미등록 참가자 리포트와 같은 역할을 화면이 한 번 더 한다.

## 실패 처리

- **조회 실패** — 펼친 자리에 오류 문구를 보이고 다시 시도할 수 있게 한다. 목록 전체가 깨지지 않는다.
- **매치가 없는 세션** — 있을 수 없지만(세션은 매치가 있어야 만들어진다) 방어적으로 "경기 없음"을 보인다.
- **참가자가 없는 매치** — 마찬가지로 빈 표 대신 문구를 보인다.

## 검증

**순수 로직**은 vitest 로 덮는다 — 참가자를 팀 순위로 묶어 정렬하는 함수, KST 날짜 계산, 세션 제목 생성.

**실데이터 검증**은 `scripts/verify-scrim-sessions.mjs` 로 한다:

- 세션이 3개이고 날짜가 07-26 / 08-02 / 08-09 이다
- 요약 뷰의 `match_count` 가 2 / 4 / 4 다
- 요약 뷰의 `participant_count` 가 68 / 64 / 64 다
- 내전 매치 10개 전부에 `scrim_session_id` 가 채워져 있다
- 폴링을 다시 돌려도 세션이 늘지 않는다

**화면 검증**은 브라우저로 한다. 08-02 내전을 펼쳐 4경기가 나오는지, 마지막 경기를 펼쳐 1등 팀이 `Ez_Gi-Man` / `Ez_SoluTion` / `Ez_Buddy` / `Ez_tktktk` 인지 확인한다 — **이 값은 관리자가 게임 결과 스크린샷과 대조해 이미 맞는 것으로 확인한 조합이다.**

## 이번 범위가 아닌 것

- **티어 랭킹 포디움** — `score` 공식을 정하는 것이 별도 주제다. 목업으로 남긴다.
- **과거 내전 입력** (2025~, 07-26 의 빠진 2경기 포함) — 별도 세션. 출처별 한계가 다르다: PUBG API 는 14일, dak.gg 는 약 2개월(`Ez_Grim` 기준 6월 16일까지), 2025 년은 관리자의 게임 결과 스크린샷뿐이고 거기엔 순위와 킬만 있다.

  **그 세션에서 스키마가 걸릴 지점을 미리 적어둔다.** dak.gg 스크린샷에는 우리가 쓰는 지표가 전부 있지만(킬·헤드·어시·딜량·DBNO·이동거리·생존), 없는 것이 둘 있다:

  - `matches.pubg_match_id` 가 기본키인데 스크린샷 출처 매치에는 진짜 matchId 가 없다
  - `match_participants.pubg_account_id` 가 `not null` 인데 스크린샷에는 닉네임만 있다

  즉 스크린샷 데이터를 넣으려면 이 두 제약을 손봐야 한다. 그리고 닉네임으로 사람을 붙여야 하므로, 그동안 닉네임을 바꾼 사람은 별칭으로 등록해줘야 연결된다. 이번 설계는 그 변경을 막지 않지만 미리 하지도 않는다 — 실제로 넣어보기 전에는 어떤 형태가 맞는지 알 수 없다.
- **`session_number` 채우기** — 과거 내전을 넣은 뒤에 한다.
- **회차별 개인 집계** — 사람별 누적 통계는 포디움과 함께 다룬다.
