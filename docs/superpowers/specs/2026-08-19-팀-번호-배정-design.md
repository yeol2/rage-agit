# 팀 구성 테이블 — 01 → 02 팀 번호 배정

## 배경

`/team-builder`(내전 팀 구성 테이블) 1단계에서 명단 업로드, 티어 자동배치, 드래그
앤 드롭으로 1~4티어 칸을 정확히 채우는 것까지 구현됐다. 이번 스펙은 "팀 구성"
버튼을 눌렀을 때 나오는 "02 팀 구성 테이블"(현재는 빈 표)에 실제 사람을 채워
넣는 것 — 각 티어 칸에 나열된 순서 그대로 1번팀부터 차례대로 배정한다.

VIP 뽑기 드래프트, 펀딩자 임시 지정, 전체/티어별 리롤은 이 스펙 이후 별도로
브레인스토밍한다 — 이번 스펙은 "기계적으로 순서대로 채우기 + DB 저장"까지만
다룬다.

## 범위

**포함**:
- `scrim_roster_entries`에 `team_number` 컬럼 추가.
- "팀 구성" 버튼 클릭 시 서버가 1~4티어 각 칸의 표시 순서(실제 티어 오름차순,
  같은 티어 안에서는 기존 배열 순서 — 드래그로 옮긴 결과가 이미 반영된 순서)
  그대로 팀 번호(1번째→1번팀, 2번째→2번팀 …)를 계산해 DB에 저장한다.
- 02 표의 각 칸을 실제 사람 네임플레이트로 채워서 보여준다.
- 참가 인원에 따라 티어당 목표 인원이 유동적이므로(예: 68명→17명) 팀 개수도
  그만큼 유동적으로 유지된다 — 이미 있는 `targetPerTierFor()` 로직을 그대로 쓴다.

**제외 (다음 스펙들로 미룸)**:
- VIP 뽑기 드래프트(순번, 픽스, 하위 VIP 뽑기 예외).
- 펀딩자 1회성 뽑기권 지정(프론트 전용, DB 미저장).
- 전체 리롤 / 티어별 리롤 버튼과 그 로직.
- 실시간 킬 집계보드(매치 종료마다 API로 킬 불러와 팀별 점수 합산) — 완전히
  별개의 하위 시스템으로 취급한다.

## 데이터 모델 (`supabase/migrations/0018_scrim_roster_team_number.sql`)

```sql
alter table scrim_roster_entries add column if not exists team_number integer;

grant select (team_number) on scrim_roster_entries to anon;
grant select (team_number) on scrim_roster_entries to authenticated;
```

- nullable — 팀 구성 전에는 전부 null.
- `scrim_roster_entries`는 이미 0016에서 컬럼 단위로 select를 잠가뒀으므로
  (deny-by-default), 새 컬럼도 명시적으로 열어줘야 anon/authenticated가 읽는다.
- uniqueness 제약은 걸지 않는다 — "팀 구성" 버튼을 다시 누르면 매번 전체를
  재계산해 덮어쓰는 방식(멱등)이라, 계산 로직 자체가 중복을 안 만든다.

## 계산 로직 (순수 함수, `lib/scrimRoster.ts`)

```ts
function assignTeamNumbers(entries: RosterEntry[]): RosterEntry[]
```

- `TIER_SLOTS`(1~4) 각각에 대해 `sortEntriesByTier(entries.filter(e => e.tierSlot === slot))`로
  정렬한 뒤, 그 배열의 인덱스+1을 `team_number`로 매긴다.
- 네 칸 모두 인원수가 같다는 전제(호출 전에 검증) 하에, 결과적으로 팀마다
  정확히 4명(티어별 1명씩)이 배정된다.
- 순수 함수 — Supabase 호출과 분리해서 유닛 테스트한다(`lib/scrimRoster.test.ts`).

## API (`app/api/scrim-roster/team-assignments/route.ts`, 신규)

`POST { rosterId: string }`

1. 서버가 해당 roster의 최신 entries를 다시 조회한다(경합 상황 방지 — 브라우저가
   들고 있는 상태가 그 사이 바뀌었을 수 있다).
2. 1~4티어 칸이 전부 `targetPerTierFor(전체 인원)`와 정확히 같은 인원인지
   재검증한다. 아니면 400과 에러 메시지를 돌려준다.
3. `assignTeamNumbers`로 계산한 뒤 각 entry의 `team_number`를 DB에 저장한다
   (service role 키 사용, 기존 `/api/scrim-roster/entries/[entryId]` PATCH와
   같은 패턴).
4. 갱신된 entries 전체를 응답으로 돌려준다(클라이언트가 재조회 없이 바로 반영).

## 클라이언트 (`components/team-builder/RosterBoard.tsx`)

- "팀 구성" 버튼의 `onClick`이 `setShowTeamTable(true)` 대신 위 API를 호출하도록
  바꾼다. 성공하면 응답으로 받은 entries로 로컬 상태를 갱신하고 `showTeamTable`을
  켠다. 실패하면 에러 메시지만 보여주고 표는 열지 않는다(버튼도 다시 누를 수
  있게 둔다).
- 버튼에 로딩 상태 추가(호출 중 비활성화 + 텍스트 "배정 중…" 등).
- 02 표의 각 `<td>`: 현재는 점선 placeholder `div`인데, 해당
  `team_number`+`tier_slot` 조합의 entry를 찾아 기존 `Nameplate` 컴포넌트로
  교체한다(왕관 등 기존 스타일 그대로 재사용). 못 찾으면(이론상 없어야 함)
  기존 placeholder를 그대로 둔다.

## 테스트

- `assignTeamNumbers` 유닛 테스트: 4칸 × N명 균등 분배, 팀 번호가 1부터 N까지
  중복 없이 배정되는지, 각 팀에 티어별로 정확히 1명씩 들어가는지.
- `scripts/verify-schema.mjs`에 0018 검증 블록 추가(컬럼 존재 + anon/authenticated
  select 권한).
- `RosterBoard` 컴포넌트 테스트: "팀 구성" 클릭 → API 성공 응답 모킹 → 02 표
  각 칸에 올바른 이름이 채워지는지.
- API 라우트는 브라우저로 수동 검증(가짜 명단 업로드 → 4칸 채움 → 팀 구성 클릭
  → 표 확인).
