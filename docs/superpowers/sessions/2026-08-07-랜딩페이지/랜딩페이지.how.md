# How: 랜딩페이지

이 문서는 코드를 어떻게 짰고, 각 부분이 왜 필요했는지, 세션이 실제로 어떤 순서로 흘러갔는지를 기록한다. "무엇을 만들었는가"는 [랜딩페이지.md](랜딩페이지.md)를 본다.

## 세션 진행 순서

### 1. 브레인스토밍 → 스펙 → 1차 구현 시도 (폐기)

`brainstorming` 스킬로 방향을 잡았다 — mapleaudit.com의 톤(다크 테마, "내 OO, 직접 확인하자" 헤드라인)을 참고하되 PUBG 맵 3D 포인트클라우드 배경으로 차별화하기로 했다. 스펙 문서 작성 후 `writing-plans` → `using-git-worktrees`(`worktree-landing-page`) → `subagent-driven-development`로 9개 태스크를 순서대로 진행: Next.js 스캐폴딩 → 콘텐츠 설정 → 이미지→포인트클라우드 변환 순수 함수(TDD) → 브라우저 이미지 로더 → 3D 배경 컴포넌트(react-three-fiber) → Nav → Hero → 페이지 조합 → 브라우저 수동 검증.

Task 9(수동 검증) 도중 실제 버그를 하나 잡았다: react-three-fiber의 `<Canvas>`가 자체적으로 `position: relative` 인라인 스타일을 강제 적용해서, `className="absolute inset-0"`가 무시되고 배경 캔버스가 문서 흐름을 차지하며 히어로 전체를 뷰포트 밖으로 밀어내고 있었다. 이 수정을 진행하던 중 사용자가 "너무 오래 걸린다, variant에 다시 물어보겠다"며 **작업 전체를 취소**했다 — 워크트리·브랜치·구현 계획을 전부 삭제하고 스펙 문서와 참고 이미지만 남겼다.

**왜 취소됐는가가 중요한 이유**: 서브에이전트 방식(태스크별 구현→리뷰→수정 루프)은 품질은 높지만 왕복이 많아 느리다. 디자인이 아직 확정되지 않고 여러 번 갈아엎을 가능성이 높은 단계(이 경우 실제로 그랬다 — 이후 variant 프롬프트를 5차례 넘게 고쳤다)에서는 직접 구현이 더 맞는 선택이었다.

### 2. variant 프롬프트 반복

이후 여러 세션에 걸쳐 variant(외부 AI 디자인 도구)에 넣을 영어 프롬프트를 함께 다듬었다. 이 단계는 코드가 아니라 "요구사항을 정확한 프롬프트로 압축하는 작업"이었다 — 컬러 팔레트, PUBG 맵 이미지 기반 3D 포인트클라우드 배경, 로고 이미지 첨부, 참고 사이트(mapleaudit.com) 레이아웃 구조를 프롬프트에 반영했다.

### 3. 직접 구현으로 전환

variant 결과물이 마음에 들지 않아 "스크린샷 보고 내가 직접 구현해줄래" 요청을 받았다. 이번엔 서브에이전트를 쓰지 않고 이 세션에서 직접 Write/Edit 도구로 구현했다.

**왜 이렇게 구조를 짰는가:**

- **`lib/siteConfig.ts`에 카피를 전부 몰아넣은 이유**: variant 스크린샷을 보고 만들다 보니 문구가 계속 바뀔 걸 알고 있었다(실제로 이후 세션에서 슬로건, 클랜원 수, 푸터 문구가 여러 번 바뀌었다). 컴포넌트 안에 문자열을 박아두면 매번 JSX를 뒤져야 하니, 처음부터 데이터와 렌더링을 분리했다.
- **`components/Logo.tsx`가 `src`/폴백 두 갈래로 갈라진 이유**: 사용자가 "로고는 있지만 나중에 바뀔 수 있다"고 명시했다. 로고 파일이 아직 없는 상태에서 컴포넌트를 완성해야 했으므로, `siteConfig.logo.src`가 빈 문자열이면 텍스트/도형 폴백을 보여주는 구조로 만들어 실제 로고 파일이 없어도 페이지가 정상적으로 보이게 했다.
- **`LocalClock.tsx`를 별도 파일로 뺀 이유**: `setInterval`로 1초마다 갱신되는 시계는 `'use client'`가 필요한 유일한 부분이다. `Nav` 전체를 클라이언트 컴포넌트로 만들지 않고, 상태가 필요한 최소 단위만 분리해서 나머지(로고, 메뉴)는 서버 컴포넌트로 남겼다. 또한 서버 렌더링 시점엔 `--:--:--`를 보여주고 클라이언트에서 마운트된 후에만 실제 시간을 채워, hydration 불일치(서버가 렌더링한 시각과 클라이언트가 렌더링한 시각이 달라서 나는 React 경고)를 피했다.
- **`siteConfig.nav[].ready` / `footer.links[].ready` 플래그를 미리 만들어 둔 이유**: 처음부터 `MEMBERS`, `MATCHES`, `RANKINGS` 페이지가 없다는 걸 알고 있었다. 나중에 페이지가 생길 때마다 컴포넌트를 다시 고치지 않고 데이터의 `ready` 값만 바꾸면 되도록 설계했다 — 실제로 대시보드 세션에서 `DASHBOARD` 항목의 `ready`를 `true`로 바꾸기만 해서 활성화했다(코드 변경은 `Nav.tsx`/`Footer.tsx`가 그 값을 실제로 읽도록 하는 부분만 필요했다).
- **Pretendard를 Google Fonts 링크가 아니라 npm 패키지로 자체 호스팅한 이유**: 외부 CDN 의존 없이 오프라인에서도 빌드되게 하려는 목적. 다만 이 과정에서 CSS에 폰트 이름만 적어두고 실제 `@import`를 빼먹는 실수를 한 번 했다 — `document.fonts.check()`나 같은 글자의 실제 렌더 폭을 비교해서(Pretendard 277px vs 폴백 폰트 320px, 실제 렌더 277px) 폰트가 정말 적용됐는지 검증한 뒤에야 확신할 수 있었다.
- **CTA 버튼과 시계 박스의 `clip-corner`(잘린 모서리) 효과**: 참고 이미지의 HUD 느낌을 살리기 위해 `clip-path: polygon(...)`을 썼다. (참고: 이후 스크롤 중 화면이 까맣게 보이는 프리뷰 버그가 있었는데, `clip-path`를 임시로 꺼봐도 증상이 그대로여서 원인이 아니었다 — 실제 원인은 프리뷰 패널 자체의 리페인트 문제였다. 아래 "버그" 항목 참고.)

### 4. 다듬기 라운드 (사용자 피드백 기반, 각 라운드마다 브라우저로 직접 검증)

여러 차례에 걸쳐 다음을 수정했다 — 매번 `npx tsc --noEmit` + 브라우저 실측(계산된 스타일, 레이아웃 좌표)으로 확인 후 커밋했다:

1. 밑줄 제거 (`확인하자.` 아래 강조선)
2. Pretendard 실제 로드 확인 및 수정
3. 상단 아이브로우 행에 가로선 + `LIVE` 상태 추가 (참고 이미지 구조 반영)
4. 네비 글자 크기 확대(11px→15px) 및 색상 변경(`#A0A0A2`) — 처음엔 너무 흐려서 안 보인다는 피드백
5. 네비 3열 그리드가 `1fr`의 최소폭 문제로 중앙정렬이 26px 어긋났던 버그 — `minmax(0,1fr)`로 수정하고 실측으로 좌우 트랙 폭이 같은지 확인
6. 클랜원 수 통계를 하단 큰 바에서 히어로 본문 아래 작은 줄로 이동 (`+12 이번 주`, 초록색)
7. 참고 이미지 기준으로 푸터를 2열 구조(브랜드+설명 / 링크)로 확장, `VERSION`을 `package.json`에서 직접 읽도록
8. `RAGE AGIT` 워드마크를 HUD 모노스페이스에서 Pretendard Bold + 좁은 자간으로 변경 (참고 로고 이미지와 맞추기 위해)
9. `SYSTEM ONLINE // SERVER: ASIA-SEOUL`, `PROTOCOL: V.0.4.21` 등 장식성 문구 제거 (variant가 지어낸 것들)

## 겪은 버그와 원인 규명

- **`npm run dev`가 켜진 상태에서 `npm run build`를 돌리면 `.next` 산출물이 꼬여 CSS 청크가 404가 난다.** 브라우저에서 배경색도 폰트도 안 먹는 것처럼 보여서 처음엔 코드 문제인 줄 알았다 — 실제로는 `.next` 삭제 후 dev 서버 재시작으로 해결됐다.
- **브라우저 프리뷰 패널에서 스크롤 시 화면이 까맣게 변하는 문제.** DOM의 `scrollY` 값은 정상이었고(`window.scrollTo`로 확인), 실제 콘텐츠도 DOM에 존재했다(`elementFromPoint`로 확인). `clip-path`를 의심해 껐다 켜봤지만 증상이 그대로였다. 최종적으로 창 크기를 살짝 바꾸면(리사이즈) 강제 리페인트가 일어나 정상으로 돌아오는 걸 확인했고, 실제 마우스 휠 스크롤 제스처로는 처음부터 문제가 없었다 — **프리뷰 패널 자체의 컴포지팅/리페인트 버그**였지, 우리 CSS 문제가 아니었다.
