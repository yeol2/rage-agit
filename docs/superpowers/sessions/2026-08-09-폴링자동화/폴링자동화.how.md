# How: 폴링 자동화 (Edge Function + pg_cron)

설계와 근거는 [폴링 자동화 설계](../../specs/2026-08-09-폴링-자동화-design.md), 실행 계획은 [구현 계획](../../plans/2026-08-09-폴링-자동화.md)을 본다. 이 문서는 실제로 해보니 무엇이 달랐는가를 적는다.

## 왜 급했는가

[매치 폴링](../2026-08-09-매치폴링/매치폴링.how.md)을 만들었지만 사람이 직접 실행해야 했다. PUBG API 는 14일치만 보관하므로 잊거나 PC 가 꺼져 있으면 그만큼이 사라진다.

이건 가정이 아니었다. 폴링을 처음 돌린 날 **07-26 내전 4경기 중 2경기가 이미 사라진 뒤**였다.

## 설계를 바꾼 것: 실행 시간이 제약이었다

Edge Function 은 실행 시간과 CPU 에 제한이 있다. 그래서 "한 번에 매치를 몇 건 여는가"부터 재봤다.

**씨앗 20명이 14일간 뛴 경기가 2721건이었다.** 내전은 그중 10경기뿐이고 나머지는 개인 랭크다. 목→일 3.5일 간격이면 한 번에 약 680건을 열어야 한다 — 제한을 넘긴다.

그런데 같은 측정이 해법도 보여줬다:

| 씨앗 | 14일 총 경기 | 내전 참가 |
|---|---|---|
| `Ez_LaPaz` | 279 | 10/10 |
| `Ez_DanE` | 226 | 10/10 |
| `Ez_MACHO-` | 60 | 10/10 |
| `Ez_Grim` | 39 | 10/10 |

**상위 20명 전원이 내전 10경기에 빠짐없이 나왔다.** 씨앗으로서의 가치는 같은데 비용이 7배 차이난다. 그래서 기준을 **"내전에 자주 나오는 사람"에서 "내전에 자주 나오면서 랭크는 적게 하는 사람"으로** 바꿨다.

경기 수는 Players 응답에 이미 들어 있어 공짜로 안다. 후보 30명을 조회한 뒤 가벼운 8명만 실제로 매치를 연다.

**결과: 680건이 14건이 됐다.** 실제 실행에서 뽑힌 씨앗은 `Ez_Code(30)`, `Ez_Grim(39)`, `Ez_purple(39)`, `Ez_2pan4pan_(52)` 같은 사람들이었고 `Ez_LaPaz(279)` 는 뽑히지 않았다.

## 사용자가 낸 아이디어와 그 한계

"전부 열어보지 말고 당일만 열어보면 안 되냐"는 제안이 나왔다. 확인해보니 **매치 목록이 최신순이라**(`Ez_Grim` 의 39경기가 `[0] 08-09` → `[38] 07-26` 로 정확히 내림차순) 구현은 쉬웠다.

다만 효과를 정확히 봐야 했다. `polled_matches` 가 이미 "한 번 본 매치는 다시 안 열게" 막고 있어서, 기준을 "마지막 폴링 이후"로 잡으면 **같은 680건**이다. 실제로 줄이려면 기준을 "오늘"처럼 더 좁게 잡아야 하는데, 그러면 **폴링이 한 번 실패했을 때 그날 내전을 영영 놓친다.** 자동화하는 이유가 유실 방지인데 유실 경로를 새로 만드는 셈이다.

사용자는 그걸 알고도 24시간을 택했다. 그래서 만회 경로를 남겼다 — 되돌아볼 기간을 `--since-hours` 로 조절할 수 있게 하고, 실패하면 디스코드로 알린다. **조용한 영구 유실을, 알림 받고 손으로 고치는 일로 바꾼 것이다.**

## 걱정했던 두 가지가 다 비껴갔다

계획에 위험으로 적어둔 것이 둘 있었는데 실제로는 문제가 없었다.

**배포가 `.mjs` 를 못 읽거나 Docker 를 요구할까** — `Docker is not running` 경고만 뜨고 `index.ts` 와 함께 `_shared/` 의 `.mjs` 세 개가 그대로 올라갔다. Node 와 Deno 가 같은 파일을 읽으므로 로직이 갈라질 수 없다.

**확장 설치가 권한에 막힐까** — `create extension pg_cron` 과 `pg_net` 이 스크립트에서 바로 통과했다. 대시보드를 열 필요가 없었다.

CLI 도 설치가 필요 없었다. `npx supabase` 로 충분했고, 액세스 토큰을 `.env.local` 에 두니 브라우저 로그인도 건너뛰었다.

## 예약해놓고 기다리지 않았다

계획에 **"예약을 몇 분 뒤로 당겨 실제로 도는지 확인한 뒤 되돌린다"**를 넣어뒀다. 매분 실행으로 걸고 기다리니 1분 만에 `trigger = 'cron'` 행이 생겼고, 16.1초에 `succeeded = true` 로 끝났다. 확인하고 `0 14 * * 0,4` 로 복원했다.

**예약해놓고 목요일까지 기다렸다가 안 돌았다는 걸 발견하는 것이 최악이다.** 이 확인이 없었으면 Vault 참조나 `net.http_post` 권한 문제를 나흘 뒤에 알았을 것이다.

참고로 `cron.job_run_details` 는 0 으로 보인다 — 예약을 지웠다 다시 만들면서 jobid 가 바뀌기 때문이다. 실제 증거는 `polling_runs` 의 `trigger = 'cron'` 행이다.

## 비밀값을 세 번 조심해야 했다

- **cron SQL 에 service_role 키가 들어갈 뻔했다.** 호출 헤더에 필요한데 마이그레이션 파일에 적으면 저장소에 들어간다. Vault 에 넣고 이름으로 참조하게 해서, 커밋되는 파일에는 비밀값이 없다.
- **함수 시크릿 등록 명령이 키를 화면에 찍을 뻔했다.** gitignore 되는 임시 파일(`supabase/.env.functions`)로 넘기고 바로 지우는 방식으로 바꿨다.
- **`.env.local` 에 웹훅을 덧붙이다 액세스 토큰을 깨뜨렸다.** 파일 끝에 개행이 없어 토큰 줄에 붙어버렸다. 분리한 뒤 네 개 키 전부 실제 호출로 동작을 확인했다.

## 운영 절차

평소에는 아무것도 안 해도 된다. 내전이 열린 날 밤 디스코드로 알림이 온다.

**미등록 참가자 알림이 오면**:

```bash
node scripts/link-alt-account.mjs <본계정IGN> <부계정IGN>
node scripts/relink-participants.mjs
```

**실패 알림이 오면** (14일 안에 해야 한다):

```bash
node scripts/poll-matches.mjs --since-hours=336
```

**예약을 바꾸려면**:

```bash
node scripts/setup-cron.mjs "0 14 * * 0,4"
```
