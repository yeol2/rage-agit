# How: 대시보드

이 문서는 코드를 어떻게 짰고, 각 부분이 왜 필요했는지, 세션이 실제로 어떤 순서로 흘러갔는지를 기록한다. "무엇을 만들었는가"는 [대시보드.md](대시보드.md)를 본다.

## 세션 진행 순서

### 1. 브레인스토밍

참고 이미지 2장(트로피/시상대 형태의 랭킹 UI, PUBG e스포츠 대회 일정 목록)을 보여주고 우리 내전 규모에 맞게 축소하는 방향으로 질문을 주고받았다. 이 과정에서 원래 계획에 없던 요구사항이 여럿 나왔다 — 티어 그룹(0~4.5, 사용자가 즉석에서 그룹핑을 4개로 압축), 다시보기 링크(관리자 수동 입력), 참여인원·경기수 표시. **브레인스토밍 스킬의 "질문 하나씩" 원칙 덕분에 이런 디테일이 계획 단계에서 다 드러났다** — 만약 곧장 구현부터 시작했다면 구현 중간에 요구사항이 계속 바뀌었을 것이다.

### 2. 선행 브랜치 정리

브레인스토밍 도중 사용자가 "랜딩페이지 브랜치를 먼저 master에 합치고 대시보드용 새 브랜치를 만들자"고 요청했다. `finishing-a-development-branch` 스킬로 처리 — 나중에 대시보드 작업이 랜딩페이지의 최신 `Nav`/`Footer`/`siteConfig` 위에서 진행되도록 순서를 맞춘 것이다.

### 3. 구현 계획

`writing-plans` 스킬로 6개 태스크를 작성했다. **태스크를 이 순서로 쪼갠 이유:**

1. `lib/dashboardData.ts` (데이터+순수 로직) — 가장 먼저. 나머지 모든 태스크가 이 모듈에 의존하므로, 데이터 모양과 계산 로직을 먼저 확정해야 컴포넌트를 짤 때 흔들리지 않는다.
2. `TierRankingPodium` — 상태(탭 선택)가 있는 유일한 컴포넌트라 클라이언트 컴포넌트로 분리.
3. `RecentScrimsList` — 상태 없음, 서버 컴포넌트로 남김.
4. `Nav`/`Footer`의 `ready` 플래그 연결 — 페이지가 실제로 생겨야 의미가 있는 작업이라 컴포넌트 태스크 뒤에 배치.
5. 페이지 조합 — 앞선 조각을 묶기만 하는 작업이라 마지막.
6. 브라우저 수동 검증.

이 저장소에 테스트 프레임워크가 아예 없었기 때문에, Task 1에 Vitest + React Testing Library 설치도 함께 넣었다 — "테스트 인프라만 따로"가 아니라 "첫 실제 모듈을 테스트로 만들면서 인프라도 같이 검증"하는 방식을 택했다.

### 4. 격리 워크스페이스 + 서브에이전트 실행

`using-git-worktrees`로 `worktree-dashboard`를 만들고(네이티브 `EnterWorktree` 도구 사용), `subagent-driven-development`로 태스크마다 새 서브에이전트를 붙여 진행했다. 6개 태스크 전부 리뷰 클린으로 통과했다.

**왜 코드가 이런 모양인가 — 태스크별로:**

- **`getTopMembers`가 `group.tiers === null`을 "전체"로 취급하는 이유**: 티어 그룹 5개 중 "전체"만 필터링이 없고 나머지 4개는 배열로 필터링한다. `null`을 특수값으로 쓰면 "필터 없음"과 "빈 배열(아무도 없음)"을 구분할 수 있다 — 빈 배열 `[]`을 "전체"로 오용하면 나중에 실수로 아무도 안 뜨는 버그와 헷갈릴 수 있었다.
- **`formatScrimDate`가 `new Date(dateISO)` 대신 `Date.UTC(...)`로 직접 조립하는 이유**: `new Date('2026-08-02')`처럼 ISO 날짜 문자열만 넘기면 로컬 타임존에 따라 하루가 밀릴 수 있다(UTC 자정으로 해석되는데, 로컬이 UTC-1 이상 뒤처진 타임존이면 전날로 보임). 요일 표시가 목적이라 이 오차가 그대로 버그가 된다. 그래서 문자열을 직접 `year/month/day`로 쪼개 `Date.UTC`로 조립하고 `getUTCDay()`로 요일을 읽었다 — 로컬 타임존이 뭐든 항상 같은 결과가 나온다. 테스트도 실제로 요일을 손으로 계산(Zeller's congruence)해서 검증했다.
- **`TierRankingPodium`/`RecentScrimsList`가 `members`/`sessions` prop을 받고 기본값만 `MEMBERS`/`SCRIM_SESSIONS`로 두는 이유**: 처음 구현할 때는 컴포넌트가 목업 배열을 직접 import해서 썼다. 최종 리뷰에서 "테스트가 실제로는 항상 같은 전역 배열을 보고 있어서, 다른 데이터가 들어왔을 때의 동작(예: 빈 배열)을 검증할 방법이 없다"는 지적이 나왔다 — prop으로 받고 기본값을 주는 구조로 바꿔서 테스트가 임의의 데이터를 주입할 수 있게 했고, 나중에 실제 API 데이터를 이 prop으로 흘려보내기도 쉬워졌다.
- **포디움 빈 슬롯에서 순위 배지(`1`, `2`, `3`)도 함께 흐리게 만든 이유**: 스펙은 "빈 자리는 —로 표시"라고만 했는데, 처음 구현은 카드 안 이름·점수만 "—"로 바뀌고 순위 숫자는 그대로 선명하게 남아 있었다. 최종 리뷰에서 "3위 배지가 선명한데 안에 아무도 없으면 시각적으로 어색하다"는 지적을 받고 `member ? 'text-accent' : 'text-accent/30'`로 배지 자체도 같이 흐리게 했다.
- **`siteConfig.dashboard`를 나중에 추가한 이유**: 처음 구현에서는 `TierRankingPodium`/`RecentScrimsList`가 "TIER RANKING", "티어 랭킹" 같은 문구를 컴포넌트 안에 직접 썼다. 랜딩페이지에서 이미 "카피는 전부 `siteConfig`에" 원칙을 세워뒀는데 대시보드 컴포넌트가 그 원칙을 깨고 있었다 — 최종 리뷰에서 이 불일치를 지적받고 `siteConfig.dashboard.tierRanking`/`recentScrims`로 옮겼다.
- **`<h1 className="sr-only">`를 페이지에 추가한 이유**: 대시보드 페이지에 시각적으로 보이는 `<h1>`이 없었다(포디움/목록 섹션은 각각 `<h2>`로 시작). 접근성 트리 상 페이지 최상위 제목이 없는 상태였는데, 화면에 새 텍스트를 더 넣긴 싫어서 스크린리더에만 읽히는 숨김 `<h1>`을 추가했다. `<title>`(브라우저 탭 제목)도 이때 같이 추가했다.

### 5. 최종 전체 리뷰

브랜치 전체 diff를 대상으로 한 번 더 리뷰를 받았다. 위에 적은 5건이 여기서 나왔다 — 태스크별 리뷰는 "이 태스크가 자기 몫을 제대로 했는가"만 보고, 최종 리뷰는 "여러 태스크가 합쳐졌을 때 프로젝트 전체 원칙(카피 분리, prop 주입 가능성, 접근성)과 어긋나는 게 없는가"를 본다 — 이번에 그 차이가 실제로 의미가 있었다.

### 6. 병합, 그리고 워크트리 정리 버그

`worktree-dashboard`에서 테스트/빌드를 재확인한 뒤 `master`로 fast-forward 병합했다. 병합 직후 워크트리 디렉터리(`.claude/worktrees/dashboard`)를 지우지 않고 뒀더니, 그 안에 남아있던 **별도의 `node_modules`(자체 React 사본)를 Vitest가 같이 스캔**하면서 `recoverFromConcurrentError`(React가 두 군데서 로드될 때 나는 에러)로 마스터 브랜치의 테스트가 깨졌다. `git worktree remove`로 지우자 즉시 24/24 통과로 돌아왔다. **병합이 끝난 워크트리는 반드시 그 자리에서 지운다.**

## 이전 세션(랜딩페이지)에서 가져온 교훈

- `vitest.setup.ts`에서 `globals: true` 없이 `@testing-library/jest-dom/vitest` 서브패스를 쓰라는 규칙을 Task 1 디스패치 프롬프트에 미리 명시했다 — 이건 처음 겪는 문제가 아니라 (다른 서브에이전트 세션에서) 한 번 겪었던 실수를 이번엔 애초에 피하도록 브리핑에 못박은 것이다.
