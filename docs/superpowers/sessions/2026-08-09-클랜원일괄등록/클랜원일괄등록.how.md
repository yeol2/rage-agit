# How: 클랜원 일괄 등록 (219명 → 211명)

설계와 결정 근거는 [클랜원 일괄 등록 설계](../../specs/2026-08-09-클랜원-일괄등록-design.md), 실행 계획은 [구현 계획](../../plans/2026-08-09-클랜원-일괄등록.md)을 본다. 이 문서는 실제로 돌려보니 무엇이 달랐는가를 적는다.

## 이 작업이 어디서 튀어나왔는가

원래는 [Phase 2(매치 폴링)](../../빅뱅배포.md) 브레인스토밍을 하던 중이었다. 폴링 주기를 정하다가 클랜 규모가 약 450명이라는 게 나왔고, 그제서야 "그 사람들이 아무 데도 등록돼 있지 않다"는 사실이 드러났다. Phase 1은 스키마와 2명만 넣고 끝난 상태였다.

디스코드 봇으로 명단을 자동 추출하는 방법을 먼저 검토했지만(봇 생성 → SERVER MEMBERS INTENT → 토큰), 설정 부담 때문에 사용자가 수동을 택했다. 그래서 티어별 역할 멤버 목록을 스크린샷으로 받아 옮겨 적었다.

**결과적으로 이게 더 나은 선택이었다.** 티어별로 받으니 세 가지가 딸려 왔다:

1. **티어 값** — Phase 1에서 `members.tier`를 만들어놓고 전부 0으로 비워뒀는데 이번에 채워졌다.
2. **화면에 찍힌 인원수** — `멤버 관리 (44)` 같은 표시가 있어서, 옮겨 적은 개수와 대조해 누락을 즉시 잡을 수 있었다. 실제로 9개 화면 전부 일치했다.
3. **디스코드 사용자명** — 회색 글씨가 사용자명이라, 별명과 사용자명을 동시에 확보했다.

## 별명은 식별 키로 쓸 수 없다

Phase 1의 `members`는 `discord_nickname`에 유일성 제약을 걸어 그것을 식별 키로 썼다. 실제 데이터 219개를 보고 나서 이게 틀렸다는 게 분명해졌다:

- 별명은 `Ez_02_(98)`, `본:Ez_SoluTion /부: Ez_Koala(93)` 처럼 형식이 제각각이고 사람들이 수시로 바꾼다
- 유일성은 디스코드가 보장하지 않는다 (219명 중엔 중복이 없었지만 그건 우연이다)

그래서 `0003`에서 `discord_username`(디스코드가 전역 유일성을 보장하는 값)을 추가해 유일 키를 그쪽으로 옮기고, 별명은 표시 전용으로 낮췄다. 지금 데이터를 갖고 있을 때 하지 않으면 스크린샷 작업을 다시 해야 해서 미룰 수 없었다.

## 마이그레이션 적용 방식을 바꿨다

Phase 1의 `0001`/`0002`는 사람이 SQL Editor에 붙여넣어 적용했다. 이번부터는 `scripts/apply-migration.mjs`가 Postgres에 직접 붙어 적용한다.

**직접 연결은 실패하고 세션 풀러로 붙었다.** `db.<ref>.supabase.co`가 IPv6 전용이라 이 환경에서 안 된다. 미리 폴백을 넣어둬서 그대로 넘어갔다 — Phase 2에서 마이그레이션을 추가할 때도 같은 경로를 쓰게 된다.

자동 적용의 진짜 이득은 편의가 아니라 **검증**이었다. `drop constraint if exists members_clan_id_discord_nickname_key`는 제약 이름을 잘못 짚어도 조용히 넘어간다. 직접 연결하니 적용 후 `pg_constraint`를 조회해 실제로 사라졌는지 확인할 수 있었고, 이번엔 이름 추측이 맞았다는 것도 그렇게 확인됐다.

## 검증에서 배운 것: 문제는 판독이 아니라 불일치였다

스크린샷에서 글자를 옮겨 적을 때 `0/O`, `1/l/I` 같은 걸 잘못 볼까 봐 23건을 "확인 필요"로 표시해뒀다. 정작 1차 조회에서 실패한 19명은 **대부분 그 23건과 무관했다.** `Ez_Raeunu`, `Ez_time`, `Ez_HoDDu` 처럼 글자가 명확한 이름들이었다.

원인을 좁히려고 두 가지를 확인했다:

1. **스팀 샤드에 있나?** — 아니었다 (10명 배치로 한 번 조회, 404).
2. **대소문자 문제인가?** — 맞았다. `Ez_NARA`로 등록된 사람의 실제 IGN은 `Ez_Nara`였다.

그래서 변형 생성기에 대소문자 패턴을 추가했다. 전수 조합은 `Ez_shinchangmin` 하나만 2^14이라 불가능하므로, 사람이 실제로 쓰는 형태만 만든다 — 전부 소문자, 전부 대문자, `Ez_` 접두사는 두고 뒷부분만 바꾼 것들. 이걸로 4명이 풀렸다(`Ez_Dotnl`, `Ez_Nara`, `Ez_vir`, `Ez_Busankalzap2`).

나머지는 사용자가 직접 검색해 6명을 더 찾아줬는데, 그 결과가 원인을 확실히 보여준다:

| 별명 | 실제 IGN | 차이 |
|---|---|---|
| `Ez_HoDDu` | `Ez_HoDDU` | 대소문자 |
| `Ez_Eunking` | `Ez_EunKing` | 대소문자 |
| `Ez_jaemoonE` | `Ez_JaemoonE` | 대소문자 |
| `Ez_KimSS쓰쓰` | `Ez_KimSS-` | 한글 자리에 `-` |
| `Ez_Pxcce` | `Ez_Pxxce` | 글자 순서 |
| `Ez_ssonz` | `Ez_Thswm` | 아예 다름 |

즉 이 작업의 어려움은 "스크린샷을 잘 읽는 것"이 아니라 **디스코드 별명과 게임 내 닉네임이 애초에 다르다는 것**이었다. 클랜에서 같게 맞추라고 안내했지만 지키지 않은 사람들이 있다. 이건 어떤 자동화로도 풀 수 없고 본인만 안다 — 디스코드 봇을 썼더라도 똑같이 막혔을 문제다.

## 재실행을 전제로 만든 것이 실제로 값을 했다

계획 단계에서 "검증 실패를 고쳐 다시 돌리는 일이 반복될 것"이라고 보고 두 가지를 넣었다:

- **등록 스크립트의 멱등성** — IGN으로 사람을 먼저 찾고 갱신/삽입을 결정한다. 실제로 205명 등록 후 6명을 추가해 재실행했고, 인원이 411명이 되지 않고 211명이 됐다.
- **검증 결과 캐시** — 확인된 사람은 건너뛴다. 이게 없었으면 재검증마다 219명을 다시 조회해 2분 반씩 버렸다. 실제로는 14명만 조회해 10초에 끝났다.

캐시는 계획에 적어놓고 처음 구현할 때 빠뜨렸다가, 첫 실행이 2분 반 걸리는 걸 보고 넣었다.

## 검증 스크립트가 틀렸던 건

첫 실행에서 "모든 IGN에 `pubg_account_id`가 채워져 있다"가 실패했다. 원인은 데이터가 아니라 검사였다 — 설계 문서에는 "관리자가 손으로 넣은 부계정은 `pubg_account_id`를 비워둬도 된다(폴링이 나중에 채운다)"고 적어놓고, 검사만 전수로 요구하고 있었다. 등록한 IGN에만 요구하도록 고쳤다.

종료 코드가 1이 아니라 127로 나오는 것도 같이 고쳤다. 출력이 아직 흘러가는 중에 `process.exit()`를 부르면 Windows에서 libuv 어서션이 터진다. `process.exitCode`만 정해두고 자연스럽게 끝나게 바꿨다.

## 등록하지 못한 8명

아래 8명은 디스코드 별명과 게임 내 닉네임이 다르고, 본인 확인이 안 돼서 이번 등록에서 빠졌다. 사용자가 검색해봐도 못 찾은 사람들이다.

| 티어 | 디스코드 별명 | 시도한 IGN |
|---|---|---|
| 0 | `Ez_Raeunu` | `Ez_Raeunu` |
| 0 | `Ez_time(99)` | `Ez_time` |
| 2 | `Ez_shinchangmin(93)` | `Ez_shinchangmin` |
| 2.5 | `Ez_2pan4pan(93)` | `Ez_2pan4pan` |
| 3 | `Ez_Xuinness(네스92)` | `Ez_Xuinness` |
| 3.5 | `Ez_Ming (04)` | `Ez_Ming` |
| 4 | `Ez_Jukatory(주현/99)` | `Ez_Jukatory` |
| 4 | `Ez_Uni(97)` | `Ez_Uni` |

**이들의 데이터가 사라지지는 않는다.** Phase 2 설계대로 폴링은 매치 참가자 64명 전원을 저장하되 등록되지 않은 사람은 `member_id`를 비워둔다. 나중에 이 8명의 실제 IGN을 알아내 등록하면 과거 기록까지 소급 연결된다.

원래 스크린샷의 219명 중 이 8명을 뺀 211명이 등록됐다. 참고로 219명은 **티어 역할이 부여된 사람만**이고, 클랜 전체(약 450명) 중 나머지는 티어가 없어 이번 범위에 넣지 않았다.

## 다음에 할 일

Phase 2(매치 폴링 파이프라인) 브레인스토밍으로 돌아간다. 중단 시점까지 정해둔 것:

- Supabase Edge Functions + pg_cron, 요일 무관 매일 1회 폴링
- 구조화된 컬럼 + 원본 JSON(`raw_attributes`/`raw_stats`) 병용 저장
- 참가자는 우리 클랜원만 저장
- 과거 데이터(2025~2026)는 복구 불가 — PUBG API는 최근 14일 목록만 주고 matchId를 따로 구할 방법이 없다. 폴링 시작 시점 이후만 쌓인다.
