# How: 클랜원 등록 (Supabase 스키마 1단계)

이 문서는 진행하면서 계속 업데이트한다. "무엇을 만들었는가"는 [클랜원등록.md](클랜원등록.md)를 본다.

## 이 세션이 왜 필요했는가

지금까지(랜딩페이지, 대시보드)는 전부 프론트엔드 + 목업 데이터였다. 실제 데이터를 다루려면 PUBG API가 뭘 주는지부터 알아야 했다 — 그래서 먼저 실제 API 키를 발급받아 `Ez_Code` 플레이어로 테스트 호출을 해봤고([pubg-api-reference.md](../../pubg-api-reference.md)), 그 결과를 바탕으로 백엔드 설계를 시작했다.

## 4단계로 쪼갠 이유

"API 연동"을 한 번에 설계하려니 범위가 너무 컸다 — 스키마, 폴링, 내전 판별, 대시보드 연동이 서로 순서대로 의존한다(스키마 없이 폴링 못 하고, 폴링 데이터 없이 판별 로직을 검증 못 한다). 브레인스토밍 스킬의 "여러 서브시스템이면 먼저 쪼개라" 원칙을 그대로 따라서 4단계로 나누고, 이번 세션은 1단계만 다루기로 했다.

## Supabase를 왜 선택했는가 (사용자가 재확인을 요청함)

프로젝트 시작할 때 이미 "Supabase + Vercel"로 정해뒀지만, 실제로 스키마를 짜기 직전에 "이게 정말 최선이냐"는 질문을 받았다. 다시 짚어본 이유:

- 클랜원·매치·참가자·내전세션이 서로 참조하는 관계형 데이터라 Postgres가 자연스럽다 (Firebase 같은 NoSQL은 이런 조인/그룹핑 쿼리에 불리하다).
- 매치 폴링(2단계)에 필요한 스케줄러가 Supabase Edge Functions에 내장돼 있어서 별도 서버/크론 인프라가 필요 없다.
- 이미 정한 Vercel 배포와 SDK 궁합이 좋다.
- 소규모 프로젝트라 서버 운영 부담을 지고 싶지 않았다.

결론은 원래 선택을 그대로 유지 — 재검토는 했지만 바뀐 건 없다.

## Supabase MCP를 지금 설정하지 않은 이유

Supabase 프로젝트 생성 화면에 MCP(Claude Code용 도구 연결) 옵션이 있었다. 연결하면 SQL Editor에 복사·붙여넣기 없이 에이전트가 직접 스키마를 적용/조회할 수 있어서 매력적이었지만:

1. 인증 단계(`claude /mcp`)가 브라우저 OAuth라 에이전트가 대신 할 수 없다 — 사용자가 터미널에서 직접 해야 한다.
2. 지금 스키마는 테이블 3개짜리로 작다. SQL Editor 복사·붙여넣기로도 충분히 빠르다.

그래서 지금은 건너뛰고, 나중에 스키마 변경이 잦아지면 (예: 2~3단계에서 테이블이 더 늘어날 때) 다시 검토하기로 했다.

## 스키마 설계에서 가장 중요했던 결정: "사람"과 "PUBG 계정"의 분리

처음 설계는 `members` 테이블에 `pubg_ign` 컬럼을 바로 넣는 1:1 구조였다(디스코드 닉네임 하나 = PUBG IGN 하나). 사용자가 자기 사례를 들어 바로 반박했다 — 실제로 `Ez_Code`와 `Ez_Codu` 두 IGN을 같이 쓰는데 디스코드 정체성은 하나뿐이다.

**왜 이게 스키마 문제인가**: 2단계(폴링)에서 매치를 가져올 때 IGN 단위로 조회하는데, 1:1 구조면 `Ez_Codu`로 뛴 경기가 어느 `member_id`에도 안 붙는다 — 새로운 사람으로 잘못 취급되거나, 아예 매칭이 안 돼서 데이터가 버려진다.

**왜 배열 컬럼(`pubg_igns text[]`)이 아니라 별도 테이블(`member_pubg_accounts`)을 선택했는가**: PUBG IGN은 전역에서 유일해야 한다(같은 이름을 두 사람이 동시에 못 쓴다) — 이건 배열 컬럼에는 걸 수 없는 제약이고, 별도 테이블의 `unique (pubg_ign)`으로는 자연스럽게 걸린다. 또한 2단계 폴링 스크립트가 "이 IGN은 어느 member_id 소속인가"를 조회하는 게 배열을 뒤지는 것보다 테이블 조인이 훨씬 직관적이다.

**결과**: `members`(사람, 디스코드 기준)와 `member_pubg_accounts`(PUBG 계정, 1:N)로 분리. 폴링 단계에서는 등록된 모든 IGN 각각으로 매치를 가져오지만, 저장은 항상 `member_id`로 연결되므로 대시보드에서는 자동으로 한 사람 스탯으로 합산된다.

## RLS(행 단위 보안)를 처음부터 켠 이유

Supabase 프로젝트 생성 화면에서 "Automatically expose new tables"는 켜져 있고 "Enable automatic RLS"는 꺼져 있는 기본값이었다. 이 조합은 "새 테이블이 기본적으로 REST API에 열려있고 행 단위 제한은 없는" 상태로 시작한다는 뜻이다 — 우리는 읽기는 공개해도 되지만 쓰기(클랜원 등록, 매치 저장)는 우리 쪽(관리자 Table Editor, 서버 폴링 스크립트)만 해야 한다. "Enable automatic RLS"도 같이 켜서 새 테이블이 기본적으로 닫힌 상태로 시작하게 하고, 읽기 전용 정책만 명시적으로 추가하는 쪽을 택했다 — 실수로 쓰기까지 열어버릴 위험을 원천 차단하는 게 나중에 문제 찾는 것보다 싸다.
