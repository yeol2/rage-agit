# 클랜원 등록 (Supabase 스키마 1단계)

> [빅뱅배포.md](../../빅뱅배포.md) 이후 단계 — 실제 백엔드(Supabase) 연동의 첫 조각. 전체 4단계 중 1단계.
>
> 1. **클랜원 등록 (이 문서)** — Supabase 스키마 + 클랜원 데이터
> 2. 매치 폴링 파이프라인
> 3. 내전 자동 판별 로직
> 4. 대시보드를 목업 대신 실데이터로 연동

## 목적

디스코드 닉네임과 PUBG IGN을 수동으로 매핑해서 저장할 곳을 만든다. 이후 단계(매치 폴링)가 "누구 매치를 가져올지" 알아내는 기준이 이 테이블이다.

## 왜 Supabase인가

- 관계형 데이터가 필요하다 (클랜원·매치·참가자·내전세션이 서로 참조) — NoSQL보다 Postgres가 자연스럽다.
- 주기적 폴링(2단계)에 Edge Functions + 스케줄러가 내장돼 있어 별도 서버가 필요 없다.
- 이미 정한 배포처(Vercel)와 궁합이 좋다 (`@supabase/supabase-js`로 바로 연결).
- 소규모 클랜 프로젝트에 서버 직접 운영은 과하다 — 무료 티어로 이 규모는 충분하다.

## Supabase MCP는 지금 설정하지 않는다

Claude Code용 Supabase MCP를 연결하면 SQL Editor에 복사·붙여넣기 없이 스키마를 직접 적용/조회할 수 있다. 다만 인증(`claude /mcp`)이 브라우저 OAuth라 에이전트가 대신 할 수 없고, 지금은 스키마가 작아 SQL Editor로도 충분히 빠르다 — **나중에 반복 작업이 늘어나면 그때 다시 검토한다.**

## 핵심 설계: "사람"과 "PUBG 계정"을 분리한다

처음엔 클랜원 1명 = PUBG IGN 1개로 설계했다가, 실제 사례로 바로 문제가 드러났다: 한 사람이 `Ez_Code`와 `Ez_Codu` 두 IGN을 같이 쓰는데 디스코드는 `Ez_Code` 하나뿐이다. 1:1 매핑이면 `Ez_Codu`로 뛴 내전은 "디스코드에 없는 사람"이 되어 통계가 갈라진다.

그래서 **한 사람이 여러 PUBG IGN을 가질 수 있는 1:N 구조**로 바꿨다. 매치를 가져올 땐 등록된 모든 IGN 각각으로 조회하지만, 저장은 항상 `member_id`(디스코드 기준 사람)로 연결한다 — 그래서 대시보드에서는 두 IGN의 기록이 자동으로 한 사람 스탯으로 합산된다.

## 스키마

**`clans`** — 지금은 RAGE 하나뿐이지만, 나중에 여러 클랜을 지원해도 테이블 구조를 안 바꾸도록 처음부터 분리해둔다.

```sql
create table clans (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  created_at timestamptz not null default now()
);
```

**`members`** — 사람(디스코드 정체성) 기준.

```sql
create table members (
  id uuid primary key default gen_random_uuid(),
  clan_id uuid not null references clans(id),
  discord_nickname text not null,
  tier numeric(3,1) not null default 0,   -- 0, 1, 1.5, 2, 2.5, 3, 3.5, 4, 4.5
  is_active boolean not null default true, -- 탈퇴자는 과거 기록은 남기고 목록에서만 제외
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (clan_id, discord_nickname)
);
```

**`member_pubg_accounts`** — 한 사람이 여러 IGN을 가질 수 있는 매핑 테이블.

```sql
create table member_pubg_accounts (
  id uuid primary key default gen_random_uuid(),
  member_id uuid not null references members(id) on delete cascade,
  pubg_ign text not null,
  pubg_account_id text,   -- PUBG API로 확인 후 채워짐, 등록 직후엔 비어있어도 됨
  created_at timestamptz not null default now(),
  unique (pubg_ign)   -- PUBG IGN은 시스템 전체에서 유일함 (같은 이름을 두 사람이 못 씀)
);
```

`pubg_account_id`를 IGN과 별도로 저장하는 이유: 닉네임은 바뀔 수 있지만 accountId는 안 바뀐다. 등록 시점에 API로 한 번 확인해두면 2단계(폴링)에서 이름 대신 accountId로 안정적으로 조회할 수 있다.

## 권한 (RLS)

읽기는 공개(대시보드가 공개 페이지니까), 쓰기는 막는다. Table Editor로 직접 입력할 때는 관리자 권한이라 문제없고, 나중에 폴링 스크립트가 쓸 때는 RLS를 우회하는 `service_role` 키를 쓴다.

```sql
alter table clans enable row level security;
alter table members enable row level security;
alter table member_pubg_accounts enable row level security;

create policy "clans_select_public" on clans for select using (true);
create policy "members_select_public" on members for select using (true);
create policy "member_pubg_accounts_select_public" on member_pubg_accounts for select using (true);
```

INSERT/UPDATE/DELETE 정책은 만들지 않는다.

## 등록 방법

Supabase Table Editor에서 관리자가 직접 행을 추가/수정한다. 별도 `/admin` 페이지는 만들지 않는다 — 개발 범위를 줄이고, Supabase 대시보드 자체가 이미 충분히 쓸만한 관리 UI다.

## 검증

스키마 SQL을 Supabase SQL Editor에 붙여넣어 적용한 뒤, 관리자가 클랜 1개 + 클랜원 1~2명(가능하면 `Ez_Code`/`Ez_Codu` 같은 멀티 IGN 케이스 포함)을 직접 넣어본다. 이후 작은 Node 스크립트로 Supabase에서 실제로 읽히는지 확인한다.

## 향후 확장 (이번 범위 아님)

- 매치 폴링 파이프라인 (2단계)
- 내전 자동 판별 로직 (3단계)
- 대시보드 실데이터 연동 (4단계)
- 클랜원 등록용 `/admin` 페이지 (당장은 Table Editor로 충분)
