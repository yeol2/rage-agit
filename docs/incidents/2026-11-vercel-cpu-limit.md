# 2026-11 Vercel 무료 CPU 한도 초과로 사이트 정지

## 요약

| 항목 | 내용 |
|---|---|
| 발생 | 2026-11-18, 사이트 전체가 `402 DEPLOYMENT_DISABLED` 로 멈춤 |
| 원인 | Vercel Hobby(무료) 플랜의 Fluid Active CPU 한도(월 4시간)를 4시간 33분으로 초과 |
| 근본 원인 | 무거운 기록 페이지의 잦은 재생성(ISR 5분), 접속마다 새로 그리는 페이지(force-dynamic), 모든 요청에 도는 미들웨어 |
| 해결 | 캐시 주기 조정, 정적 페이지 + CDN 캐시 API로 분리, 미들웨어를 라우팅 설정으로 교체 |
| 상태 | 수정은 반영함. 효과는 정지가 풀린 뒤 Usage 로 확인해야 함 |

## 무슨 일이 있었나

클랜 사이트(Next.js 14 App Router, Supabase, Vercel)가 어느 날 갑자기 열리지 않았다.
Vercel 대시보드를 보니 Hobby 플랜 사용량 중 다른 항목(함수 호출 28만/100만 등)은 여유가 있었다.
**Fluid Active CPU 한 항목만 4h33m / 4h** 로 넘어 있었다.
Hobby 는 한도를 넘으면 요금을 받는 대신 프로젝트를 멈춘다.

무료 한도는 "접속 수"가 아니라 **"서버가 실제로 계산한 시간"** 으로 잰다.
그래서 방문자가 적은 클랜 사이트도 서버가 자주 계산하면 한도를 넘을 수 있다.

## 원인 분석

### 1. 날짜별 CPU 를 쪼개 봤다

Hobby 의 Observability 는 최근 12시간만 보여줘서 페이지별 CPU 를 볼 수 없었다.
대신 Usage 의 날짜별 그래프를 "함수 / 미들웨어" 로 나눠 읽고, git 배포 이력과 맞춰 봤다.

| 날짜 | 함수 | 미들웨어 | main 배포 | 그날 들어간 것 |
|---|---|---|---|---|
| 11-11 | 1m17s | 1m09s | 0 | 평소 |
| 11-12 | 3m22s | 3m10s | 1 | |
| 11-13 | 2m45s | 2m23s | 0 | |
| 11-14 | **18m07s** | 2m07s | 11 | 클랜원별 점수 그래프, 클랜원 페이지 274개 미리 만들기, 내전 자동 확정 크론 |
| 11-15 | **45m18s** | 3m47s | 2 | 명예의 전당 |
| 11-16 | 53m34s | 6m50s | 27 | 반응속도 테스트 출시(접속마다 새로 그림), 내전 날 |
| 11-17 | 23m22s | 3m03s | 6 | |
| 11-18 | 23m45s | 0m36s | **0** | 도중 정지 |

월 합계: 함수 3h31m(77%), 미들웨어 1h01m(23%).

### 2. 읽어낸 것

- **급증 시점은 11-14 이다.** 처음엔 가장 최근에 만든 반응속도 테스트를 의심했다.
  하지만 그 기능이 생기기 전인 11-14~15 에 이미 하루 2~5분 → 20~49분으로 뛰어 있었다.
- **배포가 0번인 11-18 에도 23분.** 배포가 아니라 평소 돌아가는 재생성이 바닥 사용량을 끌어올렸다는 뜻이다.
  클랜원 상세, 점수 그래프, 명예의 전당처럼 DB 를 많이 읽고 계산하는 페이지가 5분마다(`revalidate = 300`) 다시 만들어지고 있었다.
- **반응속도 테스트의 몫은 10~15% 정도로 추정.** 11-16 이 11-15 보다 약 10분 많은 수준이었다.
  랭킹 때문에 페이지 전체를 `force-dynamic` 으로 둔 건 분명한 낭비였지만 주범은 아니었다.
- **미들웨어가 고정으로 23%.** 하는 일은 `rage-agit.vercel.app` 으로 들어오면 `rageclan.site` 로 보내는 것 하나뿐이었다.
  그런데 matcher 가 거의 모든 요청에 걸려 있었다.
  그래서 정상 도메인으로 들어온 요청(페이지, 프리페치, 데이터 요청)에서도 매번 "아니네, 통과" 만 하고 끝나는 계산이 돌았다.

## 해결

| 문제 | 조치 | 커밋 |
|---|---|---|
| 기록 페이지가 5분마다 재생성 | `revalidate` 300 → 3600. 내전 결과가 확정되면 `revalidatePath` 로 즉시 갱신하므로 최신성은 그대로 | `fd8db63` |
| 반응속도 페이지가 접속마다 렌더 | 페이지는 정적(ISR 1시간)으로 바꾸고, 랭킹은 브라우저가 `/api/reaction` 으로 따로 받음. 응답에 `Cache-Control: s-maxage=15, stale-while-revalidate=60` 을 붙여 CDN 이 들고 있게 함 | `fd8db63` |
| 메뉴바의 동적 페이지 링크가 화면마다 프리페치로 서버를 깨움 | `/team-builder` 링크만 `prefetch={false}` | `fd8db63` |
| 미들웨어가 모든 요청에 실행 | `middleware.ts` 를 지우고 `vercel.json` 의 `redirects`(host 조건)로 교체. Vercel 라우팅 단계에서 처리돼 함수 CPU 가 들지 않음 | `perf/redirect-without-middleware` |

## 유료 플랜을 고르지 않은 이유

Pro($20/월)도 CPU 를 공짜로 더 주지 않는다. 쓴 만큼(iad1 기준 CPU $0.128/시간) 계산해서 매달 $20 크레딧에서 깎는다.
이번 달 사용량이면 약 $1.9 라 돈 문제는 아니었다.
하지만 같은 트래픽에서 CPU 를 10배 넘게 쓰는 구조를 그대로 두면 사이트가 커질 때 그대로 비용이 된다.
그래서 먼저 구조를 고쳤다.

## 배운 점

- **서버리스 무료 한도는 방문자 수보다 "얼마나 자주 서버가 계산하나"가 결정한다.**
  새 페이지는 `force-dynamic` 부터 쓰지 말고 정적 + ISR + CDN 캐시를 먼저 검토한다.
- **"모든 요청에 도는 코드"는 작아도 비싸다.** 리다이렉트처럼 설정으로 되는 일은 미들웨어에 두지 않는다.
- **가장 최근 변경을 범인으로 단정하지 않는다.** 날짜별 수치와 배포 이력을 맞춰 보니 의심하던 기능보다 이틀 앞선 변경이 시작점이었다.
- **관측 도구가 부족할 때는 있는 데이터를 쪼개서라도 근거를 만든다.** 페이지별 로그 없이 날짜 × 종류 × 배포 이력만으로 원인을 좁혔다.
